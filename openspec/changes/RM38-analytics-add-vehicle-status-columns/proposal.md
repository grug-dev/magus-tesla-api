## Why

`RM38-dashboard-vehicle-status-from-metrics` (roadmap, read in full before this
proposal) moves the gateway's "latest state of a vehicle" read off
`telemetry.vehicle_snapshots` and onto the analytics module's own precomputed
`vehicle_metrics` read model — the same relocation `RM29-analytics-add-vehicle-metrics`
already did for the odometer and consumed-battery charts. Today `vehicle_metrics`
carries only three of the twelve fields the gateway's four `LatestSnapshotsByAccount`
call sites read (`battery_level_pct`, `odometer_km`, `battery_range_km`); this tier
adds the other nine — the ticket's five (with one typo corrected — see D1) plus three
more the code, not the ticket, requires (`charging_state`, `charge_limit_soc_pct`,
`captured_at` — roadmap D1) — so the analytics module becomes a complete substitute.
This tier does not touch the gateway; it only makes the substitute exist. Tier 2
switches the call sites.

Every decision below was settled with the owner via `grill-me` before the roadmap
itself was written (recorded there as roadmap D1–D7, binding, not re-opened) plus one
further decision this design pass had to make that the roadmap left open — how
`Recalculate` populates the eight new columns for a day with no computable
predecessor (D3 below).

## What Changes

- **`vehicle_metrics` gains eight nullable columns**: `locked`, `sentry_mode`,
  `car_version`, `inside_temp_c`, `outside_temp_c`, `charging_state`,
  `charge_limit_soc_pct`, `captured_at` — copied **verbatim** from the day's
  `telemetry.Snapshot` by `Recalculate`, never re-derived. All eight are always
  populated from the day's own snapshot regardless of whether that day has a
  computable predecessor (D3) — unlike the five pre-existing `_calc` columns, none of
  these eight depends on a predecessor to exist.
- **No backfill.** One migration only, all eight columns nullable, every existing row
  stays NULL forever (roadmap D2). `sentry_mode`'s NULL becomes ambiguous — "not
  reported" or "predates this migration" — documented in the column's `COMMENT ON
  COLUMN`. The other seven columns' NULL means only "predates this migration."
- **New `analytics.Reader` method, `LatestMetricsByAccount`**, returning a new
  analytics-owned domain type `VehicleStatus` (never `telemetry.Snapshot` —
  `ai/architecture.md` §2/§6) — the latest `vehicle_metrics` row per vehicle for an
  account, mirroring `telemetry.Reader.LatestSnapshotsByAccount`'s own
  `DISTINCT ON (tesla_id) ... ORDER BY tesla_id, <date-col> DESC` shape and its
  proven index reasoning (see design.md "Index Plan").
- **`UpsertVehicleMetric`, `vehicleMetricRow`, and the two mapping files
  (`recalculate.go`, `mapping.go`) extend** to carry the eight new fields through
  `Recalculate`'s write path.
- **Docs**: `internal/analytics/AGENTS.md` gains the new port method and the eight
  columns under "Data ownership"; root `README.md`'s Architecture table entry for
  `internal/analytics` is checked and updated if the new surface makes its current
  one-line description stale. `internal/analytics/README.md` does not exist today (no
  module `README.md` to update — only `internal/tesla/` has one in this repo) and this
  change does not create one — `AGENTS.md` is this module's doc-of-record, per its own
  existing "Doc-Pack (module)" convention.

## Breaking

**No — externally.** No HTTP route exists in this module (`ai/architecture.md` §3), no
gateway code changes in this tier (tier 2's job), no i18n key changes. A user sees no
difference from this tier alone.

**No — internally, additively.** `analytics.Reader` gains one new method
(`LatestMetricsByAccount`) — every existing method's signature is unchanged.
`analytics.NewReader`'s and `analytics.NewRecalculator`'s constructor signatures are
unchanged (both already take the `*pgxpool.Pool` and sibling-port dependencies this
tier needs; no new dependency is introduced). `UpsertVehicleMetricParams` (generated by
sqlc) gains eight new fields — every existing caller of `UpsertVehicleMetric` is
`recalculate.go` itself, updated in this same change.

## Modules Affected

- **`internal/analytics/`** — the only module touched by this tier. Migration, sqlc
  regeneration, `UpsertVehicleMetric`/`vehicleMetricRow`/`Recalculate` extension, new
  `LatestMetricsByAccount` port method + `VehicleStatus` domain type, `AGENTS.md`.
- **`internal/gateway/`, `internal/telemetry/`** — read, not written. Tier 2 (a
  separate change, not this one) is the only place the gateway's call sites move.

## Read Paths Affected — performance-sensitive, per `openspec/config.yaml`'s proposal
rule

- **New read path: `LatestMetricsByAccount`.** Not yet called by anything in this
  tier (tier 2 is its first caller) — but it is designed and indexed now, since the
  `database` design gate requires the full index plan up front. Read shape:
  `WHERE account_id = $1`, latest row per `tesla_id`, no date-range filter (unlike
  `ConsumedByDay`/`OdometerDeltaByDay`, which are always range-bounded). See
  design.md "Index Plan" — served by `idx_vehicle_metrics_latest (account_id,
  tesla_id, metric_date DESC)`, one new index added at the database design gate by the
  owner's explicit instruction. It removes the incremental sort the existing
  all-ascending `vehicle_metrics_account_tesla_date_unique` index would otherwise force
  on this query's mixed-direction ORDER BY; the accepted cost is a second index write
  on every nightly `Recalculate` UPSERT.
- **`Recalculate`'s write path** gains eight more columns in its existing UPSERT — no
  new query, no new read, no change to its own read shape (still the same
  1-day/2-day-widened `telemetry.Reader.SnapshotsByVehicleBetween` fetch). Off the hot
  path (nightly batch + rare manual-charge writes), per the read-heavy
  Performance-Profile's write-side latitude.
- **`ConsumedByDay`/`OdometerDeltaByDay`** — unaffected. Neither reads any of the
  eight new columns; both existing filtered queries are untouched.

## Capabilities

### Added Capabilities

- **Eight raw vehicle-status observations on `vehicle_metrics`** — locked state,
  sentry mode, software version, cabin/ambient temperature, charging state, charge
  limit, and the exact capture instant — copied verbatim from telemetry at
  recalculation time. See `specs/analytics/spec.md`.
- **`LatestMetricsByAccount`** — the analytics-owned "latest state per vehicle" read,
  replacing (for a future tier-2 caller) the need to reach into
  `telemetry.Reader.LatestSnapshotsByAccount` for this purpose. See
  `specs/analytics/spec.md`.

### Out of scope (explicitly deferred)

- **Repointing the gateway's four call sites.** Tier 2, a separate change
  (`RM38-gateway-read-dashboard-from-metrics`), depends on this tier's artifacts.
- **Backfilling historical rows.** Deferred to `openspec/roadmaps/backlog.md` §22
  (roadmap D2, rejected here as out of scope for the minimal migration the owner
  chose).
- **Any UI/badge rendering decision** (roadmap D4/D5 — `ui.Badge` pills, the 3-column
  stat grid). Tier 2's concern entirely; this tier only makes the data available.

## Testing

Per the Test-Execution-Policy: the assistant writes tests and runs `go build ./...`,
`go vet ./...`, `gofmt -l`, and the standalone guards — never `go test ./...`. The
owner runs the suite; until they do, this tier's implementation status is
**awaiting-user-verification**, never "done." See design.md "Test Contract" for the
concrete fixtures and expected values authored before implementation.

## Resolved decisions

Roadmap D1 (eight columns, `outside_temp_c` typo-corrected), D2 (no backfill, all
nullable, `sentry_mode` NULL ambiguity), D3 (all four gateway call sites — tier 2's
concern, verified here only insofar as this tier's `VehicleStatus` type must cover
the union of fields they read), D5 (badge-state table — tier 2's concern; this tier's
only obligation from D5 is modeling `Locked` as `*bool`, not `bool`), D7 (tier order
is forced) are all carried verbatim from the roadmap and not re-litigated here. This
design pass's own new decision, D3 in design.md (not roadmap D3 — see design.md for
the disambiguation), settles how `Recalculate` populates the eight columns for a
predecessor-less day, which the roadmap left to this tier to decide.

**Database design gate.** This change touches `vehicle_metrics`, an existing table
under the `database` design gate (`CLAUDE.md` "Pipeline config" — built-in, always
on). design.md carries the full column list, rationale, rejected alternatives and
index plan; the leader presents it to the owner for explicit confirmation before
Apply.
