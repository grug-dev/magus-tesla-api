## Context

Tier 3 (the core) of `openspec/roadmaps/nightly-vehicle-telemetry.md`. Tiers 1 (`tesla`) and 2
(`account`) are shipped and archived; this tier adds the module that owns collection + storage
and a thin runner.

The two ports this module consumes already exist:

- `tesla.VehicleService` (`internal/tesla/client.go`): stateless about identity. Relevant methods:
  - `ListVehicles(ctx, creds) ([]VehicleTesla, error)` — read all of an account's vehicles + their
    `State` (`"online"` / `"asleep"` / `"offline"`).
  - `VehicleData(ctx, creds, vehicleID) (*VehicleDataTesla, json.RawMessage, error)` — typed DTO
    **and** the lossless raw `vehicle_data` bytes from one request (decoded from those same bytes,
    so they can never disagree).
  - `WakeUp(ctx, creds, vehicleID) (*VehicleTesla, error)` — asks a sleeping car to come online;
    caller must poll `ListVehicles` until `State == "online"` before `VehicleData`.
  - Sentinel `tesla.ErrUnauthorized` (HTTP 401), detected with `errors.Is`.
  - `VehicleDataTesla` already exposes `BatteryRangeKm()`, `ChargeRateKmh()`, `SpeedKmh()`,
    `OdometerKm()`; `VehicleStateTesla.SentryMode` is `*bool` (nil = not reported).
- `account.Service` (`internal/account/account.go`):
  - `AllRegisteredVehicles(ctx) ([]OwnedVehicle, error)` — every vehicle across all accounts, each
    tagged with owning `AccountID` (`uuid.UUID`), `TeslaID`, `VIN`, `DisplayName`. Does NOT check
    connection liveness.
  - `AccessTokenFor(ctx, accountID) (string, error)` — a currently-valid token (refreshes/rotates
    first if needed); returns `account.ErrNoTeslaConnection` when the account has no connection.
    Caller wraps the token in `tesla.Credentials`.

Persistence follows the `account` module template (`ai/go-conventions.md` §persistence): pgx/v5 +
pgxpool, UUID PKs via `gen_random_uuid()`, module-scoped `internal/telemetry/db` generated by sqlc
into package `telemetrydb` (no other module imports it), goose migrations as the single schema
source, `pgtype`→domain conversion at the module's mapping boundary so `pgtype` never leaks out.

`cmd/web` is the wiring precedent: `config.Load()` → `pgxpool.New(ctx, dsn)` →
`account.NewService(pool, clientID, clientSecret)` → `tesla.NewClient()` → build the top-level
component → `signal.NotifyContext(SIGINT, SIGTERM)` → run → graceful shutdown. `cmd/poller` mirrors
this, substituting the telemetry scheduler for the HTTP server.

## Goals / Non-Goals

**Goals:**
- Own `vehicle_snapshots` + `poll_attempts` (append-only) in a module-scoped `internal/telemetry/db`.
- A collection service that consumes the `account` + `tesla` ports only, with per-vehicle isolation
  and a bounded wake-then-fetch flow.
- An in-app daily-at-03:30-local scheduler with graceful shutdown; a thin `cmd/poller`.
- Preserve every non-negotiable: raw JSONB + typed columns in miles, km only via `Km()`/`Kmh()`
  domain companions; no cross-module DB access; no HTML.

**Non-Goals:**
- Charge-session detection, adaptive/minutes-level polling, availability metrics — Future work in
  the roadmap; this tier only lays the foundation.
- Surfacing "connection broken" to the user (would need a new `account` write — out of scope; see D6).
- Dashboards / reads of the stored data — tier 4 (`gateway-read-stored-vehicles`) and later.
- Column encryption / retention pruning (see Risks) and any HTTP/JSON surface for this module.

## Decisions

### D1 — `vehicle_snapshots` schema: raw JSONB + extracted typed columns; nullability mirrors DTO fidelity

One immutable row per successful capture. Column types + nullability:

| Column | Type | Null? | Source (`VehicleDataTesla`) | Rationale |
|---|---|---|---|---|
| `id` | `UUID PK DEFAULT gen_random_uuid()` | NOT NULL | — | project PK convention |
| `account_id` | `UUID NOT NULL` | NOT NULL | `OwnedVehicle.AccountID` | owning account; **no FK** to `accounts` (cross-module — see D2) |
| `tesla_id` | `BIGINT NOT NULL` | NOT NULL | `OwnedVehicle.TeslaID` / `.ID` | Fleet API vehicle id |
| `captured_at` | `TIMESTAMPTZ NOT NULL` | NOT NULL | service clock at capture | when the platform captured it (not a Tesla field) |
| `raw_data` | `JSONB NOT NULL` | NOT NULL | `json.RawMessage` from `VehicleData` | lossless payload — never discard history (`AGENTS.md`) |
| `battery_level` | `INTEGER` | NOT NULL | `ChargeState.BatteryLevel` (`int`) | always present in a successful capture |
| `battery_range` | `DOUBLE PRECISION` | NOT NULL | `ChargeState.BatteryRange` (`float64`, **miles**) | rated range; km via `BatteryRangeKm()` domain method |
| `charging_state` | `TEXT` | NOT NULL | `ChargeState.ChargingState` (`string`) | e.g. `Charging`/`Disconnected`; `""` if API sends empty |
| `charge_limit_soc` | `INTEGER` | NOT NULL | `ChargeState.ChargeLimitSoc` (`int`) | charge limit % |
| `odometer` | `DOUBLE PRECISION` | NOT NULL | `VehicleState.Odometer` (`float64`, **miles**) | km via `OdometerKm()` domain method |
| `inside_temp` | `DOUBLE PRECISION` | NOT NULL | `ClimateState.InsideTemp` (`float64`, °C) | Tesla temps are already Celsius — no conversion |
| `outside_temp` | `DOUBLE PRECISION` | NOT NULL | `ClimateState.OutsideTemp` (`float64`, °C) | Celsius |
| `locked` | `BOOLEAN` | NOT NULL | `VehicleState.Locked` (`bool`) | — |
| `sentry_mode` | `BOOLEAN` | **NULL** | `VehicleState.SentryMode` (`*bool`) | **nullable to preserve absent≠false** (see below) |
| `car_version` | `TEXT` | NOT NULL | `VehicleState.CarVersion` (`string`) | software version |
| `latitude` | `DOUBLE PRECISION` | NOT NULL | `DriveState.Latitude` (`float64`) | — |
| `longitude` | `DOUBLE PRECISION` | NOT NULL | `DriveState.Longitude` (`float64`) | — |

Index: `(account_id, tesla_id, captured_at)` for the per-vehicle time-series read every dashboard
will do (latest snapshot, range over time). Append-only: no `updated_at`, no `UNIQUE` that would
block a second capture.

**Nullability rule — mirror the tier-1 DTO's fidelity.** `sentry_mode` is stored **nullable
`BOOLEAN`** because the tier-1 adapter deliberately models it as `*bool`: `nil` = the vehicle did
not report sentry, `*false` = reported off, `*true` = on. Collapsing absent into `false` would lose
that distinction and violate "never lose historical information" (`AGENTS.md`; `ai/architecture.md`
§6 comment on `SentryMode`). The telemetry domain type therefore also carries `SentryMode *bool`,
mapping `nil`↔SQL `NULL` at the boundary. Every other extracted column maps a non-pointer DTO field
that is always present on a successful `vehicle_data` fetch, so those columns are `NOT NULL`.
`raw_data` is the source of truth for anything not extracted — a column added later can be
back-filled from it, so we don't over-extract now.

**Why store typed columns AND raw JSONB (redundant on purpose).** The roadmap Decisions require
both: `raw_data` guarantees lossless history and future extraction; the typed columns give
dashboards cheap indexed reads without parsing JSON per row. Storing miles (never km) in the
columns keeps them API-native; km is derived on the read side by the domain type's companions.

### D2 — No cross-module FK on `account_id`; enforce the boundary, not a DB constraint

`vehicle_snapshots.account_id` and `poll_attempts.account_id` reference accounts owned by the
`account` module, but the columns are **plain `UUID NOT NULL` with no `REFERENCES accounts(id)`**.
A FK from a telemetry-owned table into an account-owned table is exactly the cross-module database
coupling `ai/architecture.md` §2 forbids ("no module reads another module's tables"): it would make
the telemetry migrations depend on the account schema and let a schema change in one module break
the other. Referential integrity is instead upheld by the flow — telemetry only ever writes
`account_id`/`tesla_id` values it just received from `account.AllRegisteredVehicles`. `tesla_id` is
likewise a plain `BIGINT` (the Fleet API vehicle id), not a FK to account's `vehicles` table.

### D3 — Loop structure: per-account batching (one `ListVehicles` per account, then per-vehicle wake/fetch)

`AllRegisteredVehicles` returns a flat `[]OwnedVehicle`. The collector **groups them by
`AccountID`** and processes one account at a time:

1. Resolve the account's token once via `AccessTokenFor(accountID)` → wrap in `tesla.Credentials`.
   If it returns `ErrNoTeslaConnection`, record every one of that account's vehicles as a failure
   with reason `unauthorized` and skip to the next account (no Tesla calls made).
2. Call `ListVehicles(ctx, creds)` **once** to read the current `State` of all the account's
   vehicles in a single request.
3. For each registered vehicle of that account: look up its state from the step-2 result; if
   `online`, fetch immediately; if `asleep`/`offline`, run the bounded wake flow (D4); then
   `VehicleData` → store snapshot + `poll_attempts(success)`. Isolate per vehicle (D5).

**Why per-account batching.** It minimizes paid Fleet API calls and token resolutions: one
`AccessTokenFor` and one `ListVehicles` per account instead of per vehicle, which matters for
accounts with several vehicles and respects the platform's cost/quota priorities (`AGENTS.md`
§Polling Strategy, Guiding Principle "Low operational cost"). A vehicle registered in the account
registry but absent from the live `ListVehicles` result (removed on Tesla's side) is recorded as a
failure with reason `api-error` and skipped — it is not fetched.

**Alternative — per-vehicle** (resolve token + call `ListVehicles`/wake per vehicle independently):
simpler isolation but multiplies token refreshes and vehicle-list calls by the vehicle count.
Rejected on cost. Per-account batching keeps isolation by wrapping each vehicle's fetch in its own
error-contained step (D5) while sharing the account-level calls.

### D4 — Bounded wake-then-poll: `WakeUp`, then poll `ListVehicles` until `online` or timeout (~90 s, configurable)

For an asleep vehicle: call `WakeUp(ctx, creds, teslaID)`, then poll `ListVehicles` (filtering to
that vehicle's `State`) on a fixed interval (e.g. every ~5 s) under a per-vehicle deadline
(`context.WithTimeout`, default ~90 s, env-configurable). On `online` → proceed to `VehicleData`.
On deadline → record `poll_attempts(failure, asleep-timeout)` and move on; the car is left to sleep
(no repeated wakes). The wake path uses the same per-account credentials from D3. This is the
sanctioned bounded wake exception (`AGENTS.md` §Data Access Model).

### D5 — Per-vehicle isolation + one bounded retry; every vehicle yields exactly one `poll_attempts` row

Each vehicle's collection runs inside its own recover-and-continue unit: any error (wake timeout,
`VehicleData` failure, store failure) is captured, recorded as a `poll_attempts` failure with the
mapped reason, and the loop continues to the next vehicle — one vehicle's failure never aborts the
account or the run. **One bounded retry per vehicle per run:** a transient failure
(`api-error` — e.g. a non-401 HTTP error or decode error) is retried once after a short backoff
before being recorded as a failure. `unauthorized` (401 / no-connection) is **not** retried (a
second call would fail identically and waste quota) — recorded immediately. Reason mapping:

| Condition | `outcome` | `reason` |
|---|---|---|
| snapshot captured + stored | `success` | `ok` |
| `tesla.ErrUnauthorized` or `account.ErrNoTeslaConnection` | `failure` | `unauthorized` |
| wake deadline exceeded before `online` | `failure` | `asleep-timeout` |
| other Tesla/HTTP/decode/store error (after the one retry) | `failure` | `api-error` |

Exactly one `poll_attempts` row per (vehicle, run) — it is the availability/sleep-behavior signal
the roadmap wants, so every attempt must be recorded, success or failure.

### D6 — "Flag the account connection broken" is recorded in `poll_attempts`, not pushed into `account` (out of tier-3 scope)

The roadmap failure policy says an expired/revoked token should flag the account's connection as
broken. Doing that visibly (so the dashboard can prompt the user to reconnect) would require a NEW
write method on the `account` port — a cross-module mutation telemetry must not invent, and it
would breach the "telemetry never reaches into account internals" boundary. For tier 3 the broken
connection is fully captured by a `poll_attempts` row with reason `unauthorized` (queryable later).
**Surface broken-connection to the dashboard is deferred to Future work** (needs an `account` port
addition + gateway read, a separate leader-owned change). No cross-module method is invented here.

### D7 — Scheduler: in-app daily-at-03:30-local daemon, graceful shutdown

An in-process daemon (not OS cron, per the roadmap). It computes the next run at
`hour:minute` in the configured timezone (defaults 03:30, `Local`), sleeps until then via a timer,
runs one collection cycle, then reschedules for the next day. `hour`, `minute`, and `timezone`
(IANA name, e.g. `America/Bogota`) are env-configured through `internal/config`. It honors context
cancellation: on SIGINT/SIGTERM the `signal.NotifyContext` cancels, the timer wait unblocks, an
in-flight cycle is allowed to finish under its own context (or is cancelled), and the daemon
returns — the same graceful-shutdown shape `cmd/web` uses. Missed runs (process down at 03:30) are
not back-filled in tier 3 (noted in Risks).

### D8 — Config additions live only in `internal/config`

New env the poller needs — `POLLER_SCHEDULE_HOUR` (default 3), `POLLER_SCHEDULE_MINUTE`
(default 30), `POLLER_TIMEZONE` (default `Local`), `POLLER_WAKE_TIMEOUT` (default ~90 s) — is read
in `internal/config/config.go` and passed as typed values into the scheduler/service constructors.
`os.Getenv` never appears in `internal/telemetry` or `cmd/poller` (`ai/go-conventions.md`). Editing
`internal/config` is outside the telemetry sandbox (leader-integrated, its own task).

### D9 — Proposed collection-service port signature

```go
// Collector runs one collection cycle over every registered vehicle across all
// accounts, capturing a snapshot per vehicle and recording every attempt. It is the
// telemetry module's public port; the scheduler and cmd/poller depend on this
// interface, never on the concrete implementation or the DB.
type Collector interface {
    // CollectAll runs a single cycle: enumerate all registered vehicles (via the
    // account port), and per vehicle wake-if-needed, fetch, store a snapshot, and
    // record a poll_attempts row. Per-vehicle isolation: one vehicle's failure never
    // aborts the cycle. It returns a CycleReport (counts of success/failure by
    // reason) and an error only for a whole-cycle failure (e.g. the account
    // enumeration itself failing) — never for an individual vehicle.
    CollectAll(ctx context.Context) (CycleReport, error)
}
```

`NewService(pool *pgxpool.Pool, acct account.Service, tesla tesla.VehicleService, cfg Config) Collector`
wires the store (`telemetrydb.New(pool)`) plus the two consumed ports; `Config` carries the wake
timeout (and clock, for tests). The scheduler is a separate `Scheduler` type constructed with a
`Collector` + schedule config; `Run(ctx)` blocks until `ctx` is cancelled.

## Risks / Trade-offs

- **Append-only growth / no retention.** `vehicle_snapshots` grows one row per vehicle per night
  plus a full JSONB payload; `poll_attempts` one row per vehicle per run. At current scale this is
  trivial, but there is no pruning or partitioning. Retention/partitioning and read pagination are
  **out of scope** (noted; add a retention policy or monthly-summary rollup later — `AGENTS.md`
  §"Data Retention Philosophy" allows retention policies to remove history explicitly).
- **JSONB duplicates the typed columns.** Deliberate redundancy (D1); storage cost accepted for
  lossless history + cheap reads.
- **Wake cost.** Every asleep vehicle is woken nightly — a paid call and a small battery draw,
  sanctioned by the Data Access Model. Bounded (D4) so a stuck wake can't run forever.
- **Missed nightly run not back-filled.** If the poller process is down at 03:30 that night is
  skipped (no catch-up). Acceptable for an anchor snapshot; a catch-up-on-start option is future
  work.
- **Second module's migrations + sqlc entry are repo-root edits.** `sqlc.yaml` needs a second
  `sql:` entry and the `Makefile` migration wiring must run a second `-dir`; both are outside the
  telemetry sandbox and are leader-integrated tasks. If skipped, `make sqlc` won't generate
  `telemetrydb` and `make db-setup` won't apply the telemetry migration — the build then fails fast
  (service references the missing generated package), so the omission surfaces immediately.
- **Secrets at rest.** No new tokens are stored by telemetry, but snapshots may include location.
  No encryption in tier 3 (local Postgres), same posture as the account module's tracked open item.

## Migration Plan

1. Add the goose migration `internal/telemetry/db/migrations/<ts>_init_telemetry.sql`
   (`vehicle_snapshots` + `poll_attempts` + index). Down drops both.
2. Add the second `sql:` entry to `sqlc.yaml` (package `telemetrydb`, out `internal/telemetry/db`,
   schema at the new migrations dir) and extend the `Makefile` migration wiring for the new dir
   (leader-integrated).
3. Add `query.sql` (`InsertVehicleSnapshot`, `InsertPollAttempt`, plus read helpers for tests) and
   run `make sqlc` to generate `telemetrydb`.
4. Add domain types + `Km()`/`Kmh()` companions in `telemetry.go`; implement the collector, wake
   flow, and scheduler.
5. Add config env in `internal/config` (leader-integrated); wire `cmd/poller`.
6. Tests: offline unit tests for the collector with **fake** `account` + `tesla` ports (isolation,
   reason mapping, retry, wake timeout, `sentry_mode` nil round-trip) and pure schedule-time math;
   `DATABASE_URL`-gated store tests (insert + read-back).
7. `go build ./...`, `go vet ./...`, `go test ./...` (DB tests self-skip without `DATABASE_URL`; no
   Tesla API call fires from the test run). Run `make db-setup` / `make migrate-up` to apply the
   migration in a real environment (explicit deploy step, never part of a build).
