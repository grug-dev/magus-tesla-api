## Why

The dashboard bento has two cards — "Odometer history" and "Battery history" — that render an
honest `dashHistoryEmpty()` placeholder ("Awaiting nightly snapshots") because, until RM5 tier 1
(`telemetry-add-snapshot-history-read-port`), the gateway had no way to read more than the single
latest snapshot per vehicle. With that per-vehicle history port landing, this change (RM5 **tier
2**) replaces the two placeholders with **real, responsive bar charts** for the selected vehicle
over a user-chosen window, faithfully realizing the Stitch "Dashboard - Read-Only Metric Monitor"
history charts.

The user asked for: a bar chart of odometer history (in **kilometres**), an **easily-changeable
day count** (same number of bars) that is **sent to the API** and applies to **both** the odometer
and the battery-level history, built with a lightweight client approach.

## What Changes

Primary module: **`internal/gateway/`**. Depends on RM5 tier 1's
`telemetry.Reader.SnapshotsByVehicleSince` existing.

### (a) New history API endpoint (the "new API" the user expected)

`GET /ui/dashboard/history?days=N` — an authenticated htmx **fragment** endpoint that:

- Redirects anonymous callers to `/login` (no data served), like the other `/ui/*` fragments.
- Resolves the **selected vehicle from the session** via `resolveSelectedVehicle` (the same
  mechanism the nav switcher uses — the switcher already persists the chosen `TeslaID`; the id
  therefore does **not** travel in the URL, only `days` does). The read is scoped to that
  `TeslaID` + the caller's account id.
- Validates `days` against the allowed preset set **{6, 14, 30}**; missing/invalid → **default 6**.
- Computes `since = startOfDay(now) − days days` and calls
  `telemetry.Reader.SnapshotsByVehicleSince(ctx, accountID, teslaID, since)` — **one** read, no
  N+1, miles-native.
- Renders the history block: the days selector (active preset highlighted) + the two bar charts,
  all as pre-computed display data (no math in templates).

### (b) Two responsive SVG bar charts (replacing both `dashHistoryEmpty()`)

- **Odometer history** — bars = **km driven per day** (delta: `OdometerKm(dayN) − OdometerKm(dayN-1)`,
  formatted with the existing `formatKm` helper). To render **N** delta bars the handler uses the
  **N+1** most-recent snapshots in the window (one before the first shown day seeds the first
  delta). Each bar's tooltip shows date + km driven that day + the cumulative odometer.
- **Battery history** — bars = **battery level %** (absolute 0–100) for the **N** most-recent
  snapshots. Each bar's tooltip shows date + level % + rated range km (`BatteryRangeKm()`).
- Both charts show the **same number of bars (N)**. Rendering is **hand-rolled responsive SVG**
  generated by Templ (`viewBox` + `width:100%` scales natively; native `<title>` hover tooltips) —
  **no JS chart library, no build step.** The handler pre-computes every bar's height percentage
  and tooltip string; the template only lays out `<rect>`/`<title>` from the view model. Bars use
  DaisyUI semantic colour tokens (no hardcoded hex). The empty state (`dashHistoryEmpty()`) is
  retained when a chart has too few points to draw (odometer needs ≥2 snapshots for a delta).

### (c) Days selector (the "easily changeable, sent to the API" control)

A small DaisyUI control (a `join` of three buttons **6 · 14 · 30**, default **6**, active one
highlighted) inside the history region. Each button does
`hx-get="/ui/dashboard/history?days=N"`, `hx-target="#dashboard-history"`, `hx-swap="innerHTML"`,
so changing it re-fetches **both** charts at the new window. The `#dashboard-history` region
self-loads at the default on page/fragment load (`hx-trigger="load"`), so a vehicle switch — which
already re-renders `#dashboard-content` (see "Vehicle-Scoped Cross-Region Refresh") — reloads the
charts for the newly-selected vehicle at the default window with no extra wiring.

### (d) Architecture-decision docs (the user's explicit ask)

`internal/gateway/AGENTS.md` records the **"hand-rolled SVG, no chart library"** decision (with the
rejected vanilla-JS-chart-lib alternative) **and** adds a standing convention: *any decision to add,
replace, or drop a client-side library, or to change a rendering/architecture approach, MUST be
recorded in the owning module's `AGENTS.md` as part of the same change.*

## Breaking

No. Additive: a new route + new Templ components + a new handler method that consumes the tier-1
port. No existing route, VM field, or template contract changes. The base dashboard render
(`dashboardFor` / `GET /ui/dashboard`) is untouched — the history block loads itself.

## Modules affected

- `internal/gateway/` — primary: new route, handler, Templ history components (chart + selector),
  the `#dashboard-history` region wired into the dashboard bento, and the `AGENTS.md` decision +
  convention. No new module, no DB.
- No other `internal/` module. Reads only through `telemetry.Reader` (never `telemetrydb`).

## Database Changes

None. This change reads through the tier-1 port; it adds no query, table, column, index, or
migration. The `database` design gate does not trigger.

## Read Paths Affected

One new read path per history fetch: `telemetry.Reader.SnapshotsByVehicleSince` for the **single
selected vehicle** — a bounded range scan (≤ ~N+1 rows, capped 400 in tier 1) served by the
existing `(account_id, tesla_id, captured_at)` index. It runs on the history region's `load` and on
each days-selector change; it is **not** looped across the account's vehicles (no N+1). The base
dashboard read path (`LatestSnapshotsByAccount`) is unchanged.

## Capabilities

### Added Capabilities

- **`gateway`** — new "Dashboard History Charts" requirement (delta:
  `openspec/changes/gateway-dashboard-history-charts/specs/gateway/spec.md`): the history endpoint,
  session-scoped vehicle resolution, the `days` preset validation + default, km-per-day odometer
  deltas, battery-level bars, same-bar-count, responsive-SVG / no-chart-lib rendering, no-business-
  logic-in-templates, gateway-never-imports-telemetrydb, and anonymous-redirect invariants.

### Consumed Capabilities (no change to their specs)

- **`telemetry` — Snapshot History Read Port** (RM5 tier 1) — the sole data source.

## Resolved decisions

Resolved with the user in the 2026-07-29 brainstorm (RM5 roadmap decisions RD5–RD8):

- **RD5** — Odometer bars = km driven per day (delta); N delta bars ⇐ N+1 snapshots; tooltip =
  date + km driven + cumulative odometer.
- **RD6** — Battery bars = absolute battery level %; tooltip = date + level % + rated range km.
- **RD7** — Hand-rolled responsive SVG, **no chart library**; handler pre-computes heights +
  tooltips (no template math). Vanilla-JS chart lib rejected for now.
- **RD8** — Record the no-chart-lib decision + the "decisions update AGENTS.md" convention in
  `internal/gateway/AGENTS.md`.

Open (confirm at apply): the exact preset set is **{6, 14, 30}** with default **6** (the user set
the default to 6); adjust the two non-default presets here if desired before apply.
