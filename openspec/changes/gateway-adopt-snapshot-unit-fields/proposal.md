# gateway-adopt-snapshot-unit-fields

> **Roadmap:** `RM7-store-display-units`, **tier 4 of 4**
> (`depends_on`: `telemetry-store-display-units`).
> **Generated by skill:** `opsx:propose`.
> **Originating user prompt:** *"The vision of this project is to be faster in read, slow in
> writes. So, if we are doing data transformations for unit of measures when reading them...
> that's not good. right? ... No conversions should be done when reading data. (Thousand separator
> is something on the UI scope, that's good.. but the value should be without it)"*

## Why

The gateway is where RM7's payoff lands. It is the heaviest converter in the codebase — not
because any single call is expensive, but because of how often it runs:

| Site | Runs |
|---|---|
| `handlers.go:311,313` (`mapVehicles`) | per vehicle card, per `/dashboard` and `/ui/vehicles` render |
| `handlers.go:400,405` (`mapDashboardSnapshot`) | per `/dashboard` and `/ui/dashboard` render |
| `history.go:147,154` (`buildOdometerChart`) | **twice per chart bar** — up to 30 bars per request |
| `history.go:196` (`buildBatteryChart`) | per chart bar |

After RM7 tier 2, `telemetry.Snapshot` hands these values over already in kilometres and the
`OdometerKm()` / `BatteryRangeKm()` companions no longer exist, so `internal/gateway` does not
compile. This tier adopts the fields, and in doing so **restores `go build ./...`** for the whole
repository (RM7 Decision 8).

## What Changes

- Replace every `OdometerKm()` / `BatteryRangeKm()` call in `mapVehicles`,
  `mapDashboardSnapshot`, `buildOdometerChart` and `buildBatteryChart` with a field read.
- Adopt the other renamed `telemetry.Snapshot` fields the handlers read (`BatteryLevel` →
  `BatteryLevelPct`, `InsideTemp` → `InsideTempC`, `ChargeLimitSoc` → `ChargeLimitSocPct`, …).
- **`formatKm` stays** (`handlers.go:425`). Rounding and thousands-grouping are presentation and
  belong here — exactly as the user asked ("thousand separator is something on the UI scope").
  What it must no longer do is imply a conversion: its doc comment currently says the value
  "arrives from miles via `Snapshot.OdometerKm()`" and must be corrected. The value it receives is
  a plain unformatted number, and stays one until it is rendered.
- No change to any route, view model field, template, or rendered output. The dashboard shows the
  same numbers before and after.

**Restores the build.** This is the tier whose gate is the full-tree `go build ./... && go test ./...`.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `gateway`: two requirements name the now-deleted companion methods in their normative text and
  must be corrected, or the spec would describe an API that does not exist.
  - *Dashboard renders enriched vehicle cards from stored telemetry* — states range and odometer
    are obtained "via `BatteryRangeKm()` / `OdometerKm()` companion".
  - *Dashboard odometer and battery history charts* — states the odometer delta is "converted to
    kilometres via the `OdometerKm()` companion" and the battery tooltip range via
    `BatteryRangeKm()`.

  The **behavior** in both is unchanged: the same units are displayed to the user. What changes is
  where the kilometres come from, which both requirements currently pin down explicitly.

## Impact

**Code**
- `internal/gateway/handlers/handlers.go:311,313,400,405` — companion calls become field reads;
  `formatKm`'s doc comment at `:425` corrected.
- `internal/gateway/handlers/history.go:147,154,196` — same, in both chart builders.
- `internal/gateway/handlers/handlers_test.go:231-267,560-609` and `history_test.go` — fixtures
  and expectations that are written in miles (e.g. `Odometer: 12000.0, // miles → OdometerKm = ...`).

**Docs**
- `internal/gateway/AGENTS.md:188`, which states the template does "no `OdometerKm()`/`formatKm`/
  time calls" — the method reference is stale, the `formatKm` half stays true.

**No impact on:** routes, view-model shape (`fragments.DashboardData`, `fragments.Vehicle`,
`fragments.HistoryView` keep their fields), any `.templ` file, the rendered HTML, the database, or
any other module.
