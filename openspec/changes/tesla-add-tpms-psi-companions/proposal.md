# tesla-add-tpms-psi-companions

> **Roadmap:** `RM7-store-display-units`, **tier 1 of 4** (`depends_on`: none).
> **Generated by skill:** `opsx:propose`.
> **Originating user prompt:** *"The vision of this project is to be faster in read, slow in
> writes. So, if we are doing data transformations for unit of measures when reading them...
> that's not good. right? So, I'd like to move the logic of those conversions when writting them
> into the vehicle snapshots to have the distance units as `km`, the temperature units as `C` and
> the tire pressure as `Psi`. Also, rename the affected core columns of the vehicles snapshots to
> add a suffix with the unit of measure. (e.g. XXX_km, XXX_psi, etc). No conversions should be
> done when reading data."*

## Why

RM7 moves unit conversion off the read path and onto the nightly write path. For that, the
`telemetry` write path (tier 2) needs a bar→PSI conversion it can call at capture time. The
`tesla` adapter already owns every other unit companion in the codebase — `BatteryRangeKm()`,
`ChargeRateKmh()`, `SpeedKmh()`, `OdometerKm()`, all backed by one `milesToKm` constant — but has
no pressure companion. Today the only bar→PSI conversion lives in `internal/telemetry`
(`telemetry.go:34` + the four `TpmsPressure*PSI()` methods), which is both the wrong layer for a
vendor-unit concern and, after tier 2, the wrong side of the read/write split.

Adding the companions here means that when tier 2 finishes, **every unit conversion in the
codebase lives in one module** — the adapter that owns the API-native DTOs — instead of two
(RM7 Decision 5).

This tier is purely additive: it introduces no behavior change for any existing caller and
compiles and ships on its own.

## What Changes

- Add four value-receiver companion methods to `tesla.VehicleStateTesla`:
  `TpmsPressureFLPSI()`, `TpmsPressureFRPSI()`, `TpmsPressureRLPSI()`, `TpmsPressureRRPSI()`,
  each returning `float64`.
- Add a package-level `barToPSI = 14.503773773` constant to `internal/tesla`, beside the existing
  `milesToKm`, so the factor is never hardcoded inline.
- The companions return plain `float64`, not `*float64`: the DTO's TPMS fields are plain `float64`
  (RM7 Decision 12). The nil/not-reported distinction is created one layer up in
  `telemetry.snapshotFrom`, which pointer-wraps via `ptr()` — unchanged by this tier.
- No changes to `internal/tesla/raw.go` or `cmd/explore-tesla-api/`: this adds no new Fleet API
  call, so the `tesla-exploration` sync rule in `CLAUDE.md` does not trigger.

**Not breaking.** Nothing is removed or renamed; `internal/telemetry`'s own `TpmsPressure*PSI()`
methods keep working untouched until tier 2 deletes them.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `tesla`: the adapter's unit-companion requirement currently covers distance and speed only
  (`Requirement: Metric Conversion of Distance Values`). It gains a sibling requirement covering
  tire pressure, so the adapter's obligation to expose a converted companion for every
  vendor-unit value it exposes is complete rather than distance-specific.

## Impact

**Code**
- `internal/tesla/types.go` — four new methods on `VehicleStateTesla`; one new constant.
- `internal/tesla/types_test.go` (or the module's existing unit-test file) — conversion-factor and
  zero-value coverage.

**Docs**
- `internal/tesla/AGENTS.md` — the companion-method convention section, so an agent adding a
  future vendor-unit field knows pressure is covered by the same rule as distance.

**Downstream (not this tier)**
- `internal/telemetry` consumes these in RM7 tier 2 and drops its own `barToPSI`.

**No impact on:** the database (no migration, no schema object), the Fleet API surface (no new
call, no new scope), any HTTP route, or any other module's compile.
