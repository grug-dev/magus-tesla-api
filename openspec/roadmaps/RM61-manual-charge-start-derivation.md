# RM61 — Derive the start battery % on manual charges

Source ticket: MAG-40 — https://linear.app/magus-monitor/issue/MAG-40/recalculated-battery-start
Generated by: `kkpa-dev-harness-pipeline`, from `kkpa-pickup-linear-ticket MAG-40`.

Unit tests: **included** — the owner asked for them on 2026-09-15. New tests cover the
derivation wiring, the `start_battery_source` values, and the capacity-query exclusion.

## Why

`/supercharger-stats` already fills a missing start battery %. The user types the energy
and the end %, and the module computes the start % for them. `/external-charges` does not.
There, the start % is a required field the user must always type.

MAG-40 asks for the same help on the manual charges page.

The maths already exists and is shared. `derivedStartBatteryPct`
(`internal/charging/capacity.go:110`) computes `end - energy/capacity*100`. It rounds half
away from zero and returns nothing outside `[0, 100]` instead of clamping. Today only
`VerifySession` calls it. This roadmap gives `Writer.Create` and `Writer.Update` the same
call.

## What the ticket got wrong, and this roadmap corrects

MAG-40's REQ 1 asks to "replace `packCapacityKWh` to use the effective capacity of the
previous month". **That work is already done.** MAG-32 / RM52 delivered it.

| The ticket says | The truth |
|---|---|
| `packCapacityKWh` should be changed to read the MAG-32 capacity | It already does — `internal/charging/capacity.go:47` reads `charging.monthly_effective_capacity` through `LatestMeasuredCapacity`. |
| It should read "the previous month" | It reads the **newest non-NULL** row. The job runs on day 1 for the previous month (`internal/app/processor.go:397`), so the newest row *is* the previous month whenever that month had 3 or more samples. |
| (implied) the pages need changing for REQ 1 | The word "capacity" appears nowhere in `internal/gateway`. Neither page reads or shows a pack capacity. This is a write-path concern only. |

So **REQ 1 contributes no code**. The owner confirmed on 2026-09-15 to keep
`packCapacityKWh` exactly as it is. Newest-non-NULL is deliberately better than
previous-month-only: when a month is thin its value is NULL, and newest-non-NULL falls back
to the last real measurement, while previous-month-only would fall back to the hardcoded
`62.0`.

MAG-40 also says the start % "should be optional". Inside `internal/charging` it already
is — `Entry.StartBatteryPct` is a `*int` and `RequiredFieldsFor`
(`internal/charging/validation.go:25`) never demands it, for either status. **The gateway is
what forces it**: `internal/gateway/handlers/external_charges.go:1403` says
*"start_battery_pct stays UNCONDITIONALLY required"*, and both forms set `Required: true`.
That is tier 2's work, not a schema change.

## The circular-feedback problem this roadmap must not create

`ListValidManualEntryCapacitiesForPeriod` (`internal/charging/db/query.sql:426`) feeds
`monthly_effective_capacity` from manual entries where `energy_source = 'USER'` **and**
`inferred_capacity_kwh_calc IS NOT NULL`.

`inferred_capacity_kwh_calc` is a generated column: `energy / (delta/100)`. If we derive
the start % **from** a capacity, that generated column comes back equal to the capacity we
divided by. The row's `energy_source` stays `USER`, because the user really did type the
energy. So the row would pass both filters and feed the constant back into itself.

The Supercharger side already avoids exactly this, with the `status = 'DONE'` filter at
`query.sql:447` that excludes `DONE_CALCULATED`. The manual table has no equivalent marker.
Tier 1 adds one.

## Decisions settled with the owner before any artifact was written

Captured in the Step 2 interview on 2026-09-15.

| # | Decision | Why |
|---|---|---|
| RD1 | REQ 1 changes no code. `packCapacityKWh` and `LatestMeasuredCapacity` stay exactly as they are. | The work was already delivered by MAG-32 / RM52, and newest-non-NULL survives a thin month while previous-month-only would fall back to the hardcoded 62.0. |
| RD2 | A new `start_battery_source` column on `manual_charge_entries`, values `USER` / `ESTIMATED`, module-computed and never accepted from a caller. The capacity query adds `AND start_battery_source = 'USER'`. | This table already carries two module-computed provenance columns in that exact shape — `energy_source` and `price_source` — so it is the vocabulary an agent already finds here. Reusing `status` was rejected: unlike the Supercharger table, status here is a user-picked dropdown, so a module-owned value would either appear as a choice or silently overwrite what the user selected. |
| RD3 | The edit form renders a derived start % as a **placeholder**, not as a filled value. `Update` then sees an empty start % and derives it again. | `Writer.Update` requires every mutable field on every call, so a pre-filled derived value would come back looking user-supplied and get stamped `USER` — feeding the capacity job the exact loop RD2 exists to stop. The form already has this placeholder pattern in `StartBatteryPctSuggestion`. |
| RD4 | A start % the user actually typed is never recomputed or overwritten. | Same rule the Supercharger path already states and keeps. A person's own reading must never be replaced by a computed guess. |
| RD5 | The "optional" text goes in the **field help under the input**, not in a page-level card. ES: "Opcional. Déjalo vacío y lo calculamos con la energía y el % final." EN: "Optional. | RD8 | **RD6 is reversed — the capacity disagreement IS in scope.** `charging` exposes a new public port `MeasuredCapacityKWh(ctx, teslaID) (*float64, error)`: the measured value, or nil when none exists. It never returns the `62.0` fallback. `internal/analytics` calls it and uses the measured value when present, keeping its `car_type` map as the fallback. Two new tiers, 3 and 4. | The owner asked for the fix on 2026-09-15. Keeping the map as the fallback means the number can only improve, never get worse. Moving the map into `charging` was rejected — `internal/charging` may not import `internal/account` (`db/models.go:74`, design D3), so it cannot resolve a `car_type` by itself, and its own internal callers would still fall back to `62.0`. Tiers 3 and 4 collapse into one analytics tier. | `RecentEfficiency` is the map's only consumer, and **nothing calls `RecentEfficiency`** — not a handler, not a template, not a command. `internal/gateway/handlers/history_test.go:146` panics with exactly that statement. The dashboard's efficiency tile reads `VehicleStatus.KmPerPctCalc` (`handlers.go:579`) from `vehicle_metrics`, a different number entirely. So wiring a capacity port into it would have paid real work to correct a figure no user sees. Deleting removes the second capacity definition at a lower cost and with no risk to any displayed number. It also collapses `NewReader` from six parameters to one: `RecentEfficiency` is the only method that uses six of the `reader` struct's seven fields. |

Three more points were settled by **reading the code**, not by asking, and are recorded here
so no tier re-opens them:

- **No precedence rule is needed** between the two derivations. `resolveEnergy` runs only
  when energy is nil; the new rule runs only when the start % is nil. Each needs the other's
  input to be present, so they can never both fire.
- **No `FOR UPDATE` lock is needed.** `VerifySession` locks because the nightly mirror
  rewrites `supercharger_sessions.energy_kwh` underneath it. `manual_charge_entries` has no
  background writer, and the energy arrives in the same request that writes the row, so
  there is no stored value to read first.
- **Status is unaffected.** `start_battery_pct` is not in `RequiredFieldsFor`, and
  `promoteIfComplete` never looks at it. A derived start % cannot move a row between
  `IN_PROGRESS` and `DONE`.

## Done when

A user can add or edit a manual charge, leave the start % empty, give the energy and the
end %, and the module fills the start % in. The row is marked `ESTIMATED`. That row never
reaches `monthly_effective_capacity`. A start % the user typed is still stored untouched
and still counts as capacity evidence.

And the platform holds exactly **one** definition of pack capacity, in `internal/charging`.
The `car_type` → kWh map is gone, together with the unused efficiency branch that was its
only consumer. No number any user can see changes, because nothing called that branch.
`analytics.NewReader` takes one argument instead of six.

## Future work

None open. The one deferred item — the two disagreeing pack capacities — was pulled back
into this roadmap as tiers 3 and 4 (decision RD8), so backlog item 31 was removed rather
than left as a false "pending" entry.

One thing this roadmap deliberately does **not** fix: `defaultPackCapacityKWh = 62.0` stays
a single constant inside `internal/charging`, so the module's own derivations are still
model-blind for a vehicle with no measurement. Making that model-aware needs a `car_type`,
and `internal/charging` may not import `internal/account` (`db/models.go:74`, design D3).
Raise it as its own ticket if the derived numbers ever look wrong for a non-Model-3.
