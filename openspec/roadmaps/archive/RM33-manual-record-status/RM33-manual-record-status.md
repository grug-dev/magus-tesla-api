## Intention

Manual charge entries today force the user to know the whole session up front: energy, price,
end time and end battery are all required, so a charge that is still running cannot be logged at
all. When the tiers land, a user can:

1. save a record as **IN PROGRESS** with only what they know at plug-in time, then complete it to
   **DONE** later — the required-field set is a function of the record's status;
2. leave **energy** and **price** blank — price falls back to `0`, and energy is **derived** from
   the battery delta and the pack capacity when the inputs allow it;
3. record the **odometer** at the charge event, and see what AC/DC actually mean while choosing;
4. review their entries through a **date filter** (last 7 days / this month) with **aggregation
   tiles** (sessions, energy, cost, avg kWh per session) above the table, and spot incomplete
   records at a glance from a **completeness dot** in a new Status column.

## Scope note — why this is a roadmap, not one change

The feature spans **two modules**. `internal/charging` owns the `manual_charge_entries` schema,
the `Entry` domain type, the status-conditional validation rule and the pack-capacity seam;
`internal/gateway` owns the form, the table, the date filter and the aggregation tiles. Per the
proposal rule (multi-module ⇒ roadmap), each module gets its own module-prefixed tier change.
Both gateway tiers depend on the charging tier; they do not depend on each other.

## Decisions (binding — captured in the 2026-08-29 grill-me interview with the user)

These were confirmed by the user and are authoritative for every tier's design/spec/tasks.

1. **D1 — `status` is `TEXT NOT NULL DEFAULT 'IN_PROGRESS'` with a `CHECK (status IN
   ('IN_PROGRESS','DONE'))`, and existing rows backfill to `IN_PROGRESS`.** TEXT+CHECK over a
   Postgres `ENUM` for consistency with the existing `location_kind` and `charging_type` columns
   and because altering an enum later is painful. The user chose the `IN_PROGRESS` backfill over
   the recommended `DONE`: every pre-existing row renders as unfinished until reviewed, which the
   user accepted deliberately as a prompt to re-check historical entries. Because the backfill
   value equals the default, the migration is a single `ADD COLUMN ... NOT NULL DEFAULT ... CHECK`
   statement — no two-step backfill needed. **No index**: nothing filters or sorts by status; same
   reasoning already applied to `inferred_capacity_kwh_calc`.
2. **D2 — `energy_added_kwh` drops `NOT NULL`.** Forced, not chosen: an `IN_PROGRESS` record may
   legitimately have no `end_battery_pct` (D5), so the derivation has no inputs and no honest value
   exists. The existing `CHECK (energy_added_kwh > 0)` is retained and still passes on NULL. The
   domain field becomes `*float64`.
3. **D3 — energy is derived ON WRITE, never on read**, per the project's standing "conversion
   happens once, on write" convention. When the user leaves energy blank AND both battery
   percentages are present with `end > start`, `internal/charging` computes
   `capacity * ((end_battery_pct - start_battery_pct) / 100)` and stores it. When the inputs are
   absent the column stays NULL — never a fabricated 0.
4. **D4 — a new `energy_source TEXT NOT NULL DEFAULT 'USER' CHECK (energy_source IN
   ('USER','ESTIMATED'))` column records provenance; MAG-25's generated
   `inferred_capacity_kwh_calc` column is left untouched.** Rationale, raised by the leader and
   accepted by the user: `inferred_capacity_kwh_calc` divides energy by the battery delta, so a row
   whose energy was itself derived from `capacity * delta/100` returns *exactly the capacity
   constant* by algebra. The user's stated plan is to later replace the 62 kWh constant with the
   **average of the inferred capacities**, which closes the loop — derived rows would feed the seed
   value back into the average and it would stop converging on the pack's real capacity (3 real
   rows averaging 68 plus 7 derived rows gives 63.8, dragged toward the seed). Recording provenance
   now is additive and costs nothing today; the future averaging feature filters
   `WHERE energy_source = 'USER'`. It cannot be reconstructed after the fact — once `31.0` is
   stored there is no way to tell a typed value from a derived one. Changing the generated column's
   expression inside this ticket was rejected as a table-rewriting migration that alters MAG-25's
   behaviour out of scope.
5. **D5 — the status→required-fields rule is a single declarative set in `internal/charging`,
   enforced by the domain and read by the gateway.** One exported lookup (`RequiredFieldsFor(status)
   []Field`) is the single source of truth: `Writer.Create`/`Update` enforce it for every caller,
   and the gateway imports the same set to drive which inputs render as required/disabled. Adding a
   field to the skip set later is a one-line, one-file change that both layers follow — the ticket's
   "easy to maintain" requirement. Initial `IN_PROGRESS` skip set: `ended_at`, `end_battery_pct`.
   **Confirmed at the 2026-08-29 design gate:** the skip set means both fields are **REQUIRED when
   status is `DONE`**. This is a real tightening — `ended_at` is optional today in both the DB and
   the form — and the user confirmed it explicitly. Consequence: tier 2 renders `ended_at` as
   required once DONE is selected, and an existing DONE record with no `ended_at` cannot be
   re-saved without filling it in.
   **No DB CHECK backstop**: it was offered and rejected, because every future change to the skip
   set would then require a migration, working against the maintainability requirement.
6. **D6 — `odometer_km INTEGER NULL CHECK (odometer_km >= 0)`.** The `_km` suffix is mandated by the
   project's display-unit convention. The user chose INTEGER over the recommended `NUMERIC(10,1)`:
   whole kilometres are what the user reads off the dash. No index. It lives on
   `manual_charge_entries` because it is an observation made *at that charge event*, not current
   vehicle state.
7. **D7 — `price` stays `NUMERIC(14,2) NOT NULL`; the gateway coerces empty → `0`.** No migration
   for price at all. The form drops `required`, keeps `min="0"`, and `parseChargeForm` maps empty to
   `0`. `currency` stays `NOT NULL DEFAULT 'COP'` and remains the disabled, hardcoded input it
   already is (MAG-5/D5). The COP hint renders as a **suffix inside the price input**.
8. **D8 — the pack capacity sits behind `packCapacityKWh(ctx, vin) (float64, error)` in
   `internal/charging`**, returning a hardcoded `62.0` today. The ctx+error signature is deliberate
   future-proofing: the ticket's whole reason for demanding a function is that a DB/module-backed
   lookup replaces it later, and that lookup needs both — so the swap becomes a one-body change with
   zero caller churn. A `TODO(MAG-18)` comment names what it is pending on. The KB note goes to
   `kkpa/context/workflows/manual-charge-crud.md`.
9. **D9 — the table's Status column carries BOTH signals: a coloured dot for data completeness and a
   text badge for IN_PROGRESS/DONE.** The ticket used the word "Status" for two different things;
   one column showing both removes the ambiguity and makes "DONE but missing a price" visible.
   Green ⟺ every required-for-DONE field present AND energy present AND price present.
10. **D10 — the completeness colour is computed in the Go view model**, as a `ChargeEntryVM` field
    set in `chargeEntryVMFromEntry`, not in JS. The gateway's standing convention is that handlers
    pre-compute and templates do no arithmetic; this also keeps it unit-testable without a browser
    and lets the tooltip resolve through `i18n.T` like every other label. The ticket's "can be done
    on the front end" is still satisfied — it means no server round-trip, which this meets.
11. **D11 — the battery range column is ADDED ALONGSIDE the existing `BatteryDelta` column.** The
    user chose to keep both: `22% → 70%` for the absolute range and `+48%` for the delta.
12. **D12 — the date-change handler preserves the time portion.** A client-side listener on the date
    input rewrites only the `YYYY-MM-DD` part of `started_at`/`ended_at`, keeping `HH:MM`. An empty
    datetime stays empty — never auto-filled. Clobbering to midnight was rejected as silently
    discarding real user input.
13. **D13 — the date filter and the tiles are computed server-side from ONE query.** The handler
    resolves "last 7 days" (default) / "this month" into `from`/`to` using the same
    **browser calendar day** mechanism the form defaults already use (`browserToday`, not UTC), then
    calls the **existing** `Reader.ListEntriesByVehicleBetween` — no new port method. The four tiles
    are summed in the handler over that same result set, so the numbers provably match the rows
    shown. A single COP total (manual entries are COP by construction), unlike the superchargers
    component which must never sum across currencies. Empty range renders `0` and `—`.
14. **D14 — empty values render as the em-dash `—`, not the ticket's literal `--`.** `—` is already
    the project-wide empty placeholder (`dashStat`, `superchargerCostValue`, every
    `SuperchargerSessionVM` label). The ticket's `--` is read as plain-text shorthand for it.
15. **D15 — the form-clearing bug is a server-side re-render bug, not an htmx swap issue.**
    Root-caused during the interview: `ChargeCreate` returns
    `renderError(c, 422, fragments.ChargeCreateForm(d, validationErrors))` (`handlers/charges.go:208`)
    with a **freshly built** `ChargesPageData`, and `ChargeCreateForm` has no mechanism to echo
    submitted values — so every input except the date defaults renders blank. The fix carries the
    submitted raw values back into the error re-render. htmx already swaps on 4xx here (that is why
    the blanking is visible), so no `hx-swap`/`beforeSwap` change is needed.
16. **D16 — AC/DC clarification goes in the option text itself.** ES: `AC — Carga lenta
    (casa/destino)` / `DC — Carga rápida (Supercargador)`. EN: `AC — Slow charging
    (home/destination)` / `DC — Fast charging (Supercharger)`. The DB still stores `'AC'`/`'DC'`;
    only `value=` is unchanged. Both languages are mandatory per the i18n rule.

## Design gate — confirmed 2026-08-29

The user reviewed the tier-1 DDL (three added columns, `energy_added_kwh` NOT NULL dropped, no
indexes, `inferred_capacity_kwh_calc` untouched), its rationale and its index plan, and
**approved it**. Two follow-up questions the worker raised were settled at the same gate:

- **D5's DONE semantics** — confirmed: DONE requires both `ended_at` and `end_battery_pct` (folded
  into D5 above).
- **D17 — the `EnergyAddedKWh *float64` compile break is fixed inside tier 1, as task `L1`.**
  Making the field a pointer breaks `internal/gateway`'s compilation at ~14 call sites. A
  charging-scoped worker cannot cross the module boundary to fix it, so tier 1 alone would leave
  `go build ./...` red repo-wide and its reviewer gate unenforceable (the reviewer runs that
  signal). `L1` is a **minimal, purely mechanical** nil-handling fix dispatched to a gateway-scoped
  worker in tier 1's final wave — no feature change. All real gateway work stays in tiers 2 and 3.
  Rejected: merging tiers 1 and 2 (tier 1 stops being a clean schema unit), and accepting a red
  build (blocks the user from running the suite between tiers).
