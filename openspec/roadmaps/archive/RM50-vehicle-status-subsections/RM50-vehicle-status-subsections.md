## Intention

The `/dashboard` "Vehicle Status" panel today shows one flat row of four stat tiles. When every
tier lands it shows three named subsections instead:

1. **Travel Progress** — the latest distance travelled (green up icon) and the latest battery
   drain (red down icon), both for the most recent computed day.
2. **Tire pressure (PSI)** — one value per wheel, each with an up/down icon showing the change
   against the previous day.
3. **Interior / Exterior** — the existing temperature tiles, regrouped under their own heading.

The platform also gains four raw tyre-pressure columns and four tyre-pressure delta columns on
`vehicle_metrics`, so the panel reads one precomputed row per vehicle and computes nothing at
request time.

## Scope note — why this is a roadmap, not one change

The feature spans **two modules**. `analytics` owns `vehicle_metrics`, the new columns, the delta
maths and the read port. `gateway` owns the panel that displays them. Per the proposal rule
(multi-module ⇒ roadmap) each module gets its own module-prefixed tier change.

Tiers **alternate** between the two modules on purpose (RD5), so the user sees a working screen
after tier 2 instead of after the last tier.

## Decisions (binding — settled with the user on 2026-09-08, before any artifact was written)

These were confirmed by the user and are authoritative for every tier's design, spec and tasks.
A tier worker must not re-open them.

### RD1 — Tyre-pressure variance is stored as four scalar `_calc` columns, not a JSONB blob

Column names: `tpms_pressure_fl_psi_calc`, `tpms_pressure_fr_psi_calc`,
`tpms_pressure_rl_psi_calc`, `tpms_pressure_rr_psi_calc` — unit before `_calc`, mirroring the
existing `distance_traveled_km_calc`.

**Why:** the project's unit-suffix rule needs a real column to carry `_psi`; a JSONB blob has
nowhere to put it. `sqlc` gives a typed `*float64` per column, while JSONB gives a `[]byte` the
gateway must unmarshal by hand, losing the compile-time check. The set is a fixed four wheels, so
JSONB buys no flexibility. Four columns also keep the existing closed vocabulary that an agent
copies instead of inventing a new JSON shape.

**Rejected:** one JSONB column holding four values.

### RD2 — Existing rows are backfilled by a cross-schema SQL migration

The migration runs `UPDATE analytics.vehicle_metrics … FROM telemetry.vehicle_snapshots`.

**This is a deliberate, informed deviation from the analytics spec requirement "No Cross-Module
Database Access".** The user chose it after being shown the recommended alternative and being told
it breaks that written rule. It is a **one-off data backfill**, not a new runtime read path: Go
code must still never reach across the module boundary.

Facts verified before the decision — a tier worker relies on these and does not re-derive them:

- `make boundary-guard` does **not** catch this. It only greps `internal/gateway/` for an
  `internal/telemetry` Go import. No `// boundary:allow:` comment is needed.
- The migration is executable. Every module owns a real Postgres schema and `db-setup` makes the
  single app role the owner of all of them, so no `GRANT` is required.
- `MIGRATIONS_DIRS` order is account → telemetry → charging → analytics. So
  `telemetry.vehicle_snapshots` already exists when the analytics migration runs. Each tier that
  touches the schema must re-check this and record the result, per CLAUDE.md.

**Rejected:** delete the `vehicle_snapshots` rows from `vehicle_metric_watermarks` and let the
next nightly `Reconcile` rebuild history. This was the recommendation — it needs no cross-module
SQL and is self-healing — but the user chose the direct migration.

### RD3 — The tyre-pressure delta compares against the previous day

Same shape as `distance_traveled_km_calc`: derived in the pure-maths layer from `prev` versus
`cur`. NULL when the day has no predecessor.

Known and accepted: tyre pressure moves with air temperature, about 1 PSI per 5.5 °C. So the
delta partly tracks the weather, not only a real leak. This is accepted, **not** a defect, and no
tier may "fix" it by adding a threshold.

**Rejected:** a dead-zone that hides changes under ~1.5 PSI. **Rejected:** comparing against the
vehicle's recommended cold pressure, which would need a new per-vehicle setting.

### RD4 — `/design` runs at the first gateway tier and must target Templ + htmx

The user confirmed running the `/design` skill to produce **three** layout suggestions for the
panel. It runs at **tier 2**, the first gateway tier — not during an analytics tier, because the
layout does not change what data analytics must produce.

The output must be buildable with the project's real stack: **Go Templ components + htmx**, using
the existing `internal/gateway/templates/ui/` kit and semantic theme tokens. It is not free-form
HTML/CSS. A suggestion that cannot be expressed in the `ui/` kit is not a valid suggestion.

### RD5 — Tiers alternate analytics → gateway → analytics → gateway

The user chose the ticket's own step order over grouping all backend work first. Cost: two
gateway tiers instead of one. Benefit: a visible screen change after tier 2, and a natural stop
point after every tier — which is what the ticket asked for ("after you finish a step, stop until
I approve").

### RD6 — Labels use semantic theme tokens, never the raw colour from the ticket

The ticket suggests `rgb(231 189 184 / var(--tw-text-opacity, 1))`, read off an `apex`-theme
screenshot. That value is **not** hardcoded. `make ui-guard` forbids raw colour values and inline
DaisyUI component classes. The intent maps to the existing semantic token so `graphite` and
`halloween` render correctly too.

### RD7 — Step 2 of the ticket names the wrong endpoint; the artifacts carry the correction

The ticket says the Travel Progress data comes from `GET /ui/dashboard/history`. It cannot. That
endpoint renders **only** the `#dashboard-history` charts region below the panel.

The Vehicle Status panel is a separate request — `GET /dashboard` and `GET /ui/dashboard`
(`Handler.dashboardFor`) — fed by `analytics.Reader.LatestMetricsByAccount` →
`analytics.VehicleStatus` → `mergeVehicleStatuses` → `mapDashboardSnapshot` →
`fragments.DashboardData`. Every tier reads that path, not the history path.

### RD8 — No cosmetic tests

The user said "DO not add cosmetic tests". Apply the project's own rule: no template tests coupled
to markup, CSS classes, ARIA, or element placement. The pure delta maths in
`internal/analytics/consumption.go` **is** worth a unit test. Claude writes tests and never runs
the suite — the owner runs it and reports.

## Verified codebase findings (checked before the roadmap; tiers do not re-derive these)

- **`telemetry.Snapshot` already exposes the four TPMS fields on its public port** —
  `TpmsPressureFLPSI`, `TpmsPressureFRPSI`, `TpmsPressureRLPSI`, `TpmsPressureRRPSI`, all
  `*float64` in PSI (`internal/telemetry/telemetry.go`). So **tier 1 needs no change to
  `internal/telemetry` at all.** It is analytics-only: four raw columns plus a verbatim copy in
  `deriveVehicleMetrics`. Exact precedent: `MaxRangeChargeCounter` (MAG-47).
- **The raw TPMS columns follow the RM38 status-observation rule, not the `_calc` rule.** They are
  copied verbatim onto every row, including a predecessor-less day — never re-derived, never
  unit-converted, never given a default. The `_calc` delta columns (RD1) follow the opposite rule:
  NULL when there is no predecessor.
- **Travel Progress needs no migration and no new query.** `distance_traveled_km_calc` and
  `consumed_pct` are already columns on `vehicle_metrics`. The work is to add both to the
  `LatestMetricsByAccount` SELECT, run `make sqlc`, add two pointer fields to
  `analytics.VehicleStatus`, and format them onto the dashboard view model.
- **The knowledge base must be corrected in the same tiers.**
  `kkpa/context/entities/vehicle-metrics/guide.md`,
  `kkpa/context/use-case/gateway/read-dashboard-bento.md` and
  `kkpa/context/input-port/gateway/dashboard.md` all describe surfaces these tiers change — the
  column list, `VehicleStatus`'s field list, and the stat-tile row. Never touch
  `openspec/changes/archive/`.

### RD9 — The panel layout is `/design` Option B (settled 2026-09-08, tier 2)

Inside the panel card, an inner 12-column grid. Left column (`md:col-span-4`): the vehicle
image, then the Odometer and 100% Charges tiles stacked. Right column (`md:col-span-8`): the
three named subsections stacked, each with a `ui.SectionHeader`. Tire pressure is a **2x2**
grid, not one row of four — the right column is too narrow for four.

**Why:** the user picked it from three artboards drawn with the app's real tokens. It is the
most compact option, so the 8-col hero stays close in height to the 4-col column beside it.

**Cost accepted:** "which wheel" is harder to read than the rejected wheel-map option.

### RD10 — Each tyre tile also shows the numeric delta

The up/down icon sits beside the value; the number (e.g. "+0.4 vs prev. day") goes on the
tile's `Desc` line. This applies to tier 4's tyre tiles.

**Why:** the ticket asked only for an icon, and the user confirmed keeping the number. Tier 3
computes it anyway, so it costs two i18n keys and no new data.

**Not applied to Travel Progress.** Those two values are already single-day deltas, so a line
underneath would repeat the number the value already shows.

### RD11 — The `ui/` kit gained two things in tier 2

`ui.Icon` has `trending_up` and `trending_down`. `ui.StatTileProps` has `Trend string` —
`"up"`, `"down"`, or empty for no icon.

**Why:** the arrows did not exist, and `StatTile` had no slot for one. A page hand-writing that
markup would bypass the kit, which the module forbids.

### RD12 — Tier 3 backfills the tyre deltas by self-join, inside analytics' own schema

The migration updates `analytics.vehicle_metrics` from itself, computing each row's four delta
values against the previous day's row.

**Why:** tier 1 already copied the raw `tpms_pressure_*_psi` columns into `vehicle_metrics`, so
the delta is computable without leaving the module's own schema. **Unlike RD2 this is NOT a
boundary deviation** — no cross-schema read, nothing to record as an exception.

**Rejected:** (a) no backfill, letting the nightly `Reconcile` fill old rows — it depends on
Reconcile recalculating full history as a side effect of the supercharger watermark, and if
that side effect changes, old rows stay NULL and nobody notices; (b) resetting the
`vehicle_snapshots` watermark — it rewrites every derived row instead of only the new columns.
