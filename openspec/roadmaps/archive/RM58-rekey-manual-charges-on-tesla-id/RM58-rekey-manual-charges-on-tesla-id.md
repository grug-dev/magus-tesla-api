# RM58 — Re-key manual charge entries on tesla_id

Source ticket: MAG-68 — https://linear.app/magus-monitor/issue/MAG-68/5-demote-chargingmanual-charge-entriesaccount-id-to-created-by-account
Parent: MAG-63 (step 5 of 7). Blocker MAG-66 (the authorization seam) is done.
Generated by: `kkpa-dev-harness-pipeline`, from `kkpa-pickup-linear-ticket MAG-68`.

Unit tests: **excluded** — the ticket says so directly. Existing tests are updated where a
signature changes; no new test files.

## Why

`charging.manual_charge_entries` is keyed on `account_id`. That is wrong for data about a
car. A charge happened to a vehicle, so `tesla_id` is the key.

But a **person typed** this row. That authorship is worth keeping. So the column is not
dropped, like RM57 dropped it from the two Supercharger tables. It is **demoted**: renamed
to `created_by_account_id`, kept as a record of who entered the charge, and never used as a
key or a read filter again.

One transitional exception, for one tier only: tier 1 keeps the column as the write-path
guard so no commit ships an unauthorized update or delete. Tier 2 removes it. See "The gap
this roadmap must not open" below.

## The decision that sets the scope

**The reads become car-wide.**

Today `internal/analytics` reads a car's manual charges filtered by account. After this
roadmap it reads every manual charge for that car, whoever typed it.

This is a real behaviour change, not only a schema change. If two accounts are registered
to the same vehicle, each account's `vehicle_metrics` values change.

The owner chose it, and it makes the two charging sources agree. RM57 already made
supercharger sessions car-wide: `analytics` calls `ListSessionsByVehicleBetween(ctx,
teslaID, ...)` with no account. Manual entries were the last charging source still
filtered by account.

## What the ticket got wrong, and this roadmap corrects

MAG-68 said `internal/gateway/handlers/external_charges.go` is the only consumer. It is
not. `internal/analytics` calls three of the per-vehicle read ports:

- `internal/analytics/reader.go:146` — `ListEntriesByVehicle`
- `internal/analytics/recalculate.go:163` — `ListEntriesByVehicleBetween`
- `internal/analytics/recalculate.go:283` — `ListEntriesByVehicleUpdatedSince`

So three modules change, not two. The ticket description was corrected in Linear on
2026-09-14.

## Facts already checked — do not re-derive

- `authorizeVehicle` is at `internal/gateway/handlers/handlers.go:1061` and returns a
  `vehicleref.Ref`. That is MAG-66's seam.
- `vehicleref.All(owned []int64) []Ref` and `vehicleref.TeslaIDs(refs []Ref) []int64`
  already exist (`internal/vehicleref/vehicleref.go:39,50`). They are where the gateway
  gets the `tesla_id` array for `ListEntriesByVehicles`.
- `make vehicleref-guard` allows `vehicleref.Authorize` and `vehicleref.All` only inside
  `internal/vehicleref`, in `_test.go` files, and in the gateway's `authorizeVehicle`.
- The write ports today are `Update(ctx, e Entry)` and `Delete(ctx, accountID, id)`. The
  read ports are the four `ListEntries*` methods on `Reader`
  (`internal/charging/charging.go`).
- **There is no FK on the column.** `20260718000001_add_manual_charge_entries.sql` says
  "No cross-module FK on account_id or tesla_id". It is `NOT NULL` and stays `NOT NULL`.
  Nothing about `ON DELETE` changes.
- The gateway **already** resolves an entry's `tesla_id` before writing, through
  `fetchEntryTeslaIDAndChargedOn` and `fetchEntryVM`. Both list entries and match on id —
  the "no GetEntry port" shape. Once that list is scoped to the account's own vehicles,
  the lookup proves ownership by construction.
- `MIGRATIONS_DIRS` order is `account → telemetry → charging → analytics`. Every module
  shares ONE `goose_db_version` table, keyed by version. A `20260914…` migration sorts
  cleanly after MAG-67's `20260912…`.
- `make migration-guard` passes. It warns about the known un-renumbered collision
  `20260720000001`, which sits in this same `charging` migrations folder. That is backlog
  item 21, pre-existing, and not this roadmap's job.

## The gap this roadmap must not open

Tier 1 was first written to drop the `account_id` predicate from `UpdateEntry` and
`DeleteEntry`, exactly as the ticket says. That leaves the manual-charge write path with
**no authorization at all** until tier 2.

It is not theoretical. `ExternalChargeRowDelete` calls `fetchEntryTeslaIDAndChargedOn` only
to learn which day to recalculate. Its own comment says the delete still proceeds on a
lookup miss (`internal/gateway/handlers/external_charges.go:571`). So the SQL predicate is
the only guard there is.

The owner chose to keep the predicate in tier 1 and remove it in tier 2, together with the
`tesla_id` guard. It costs two SQL lines. No commit is ever exposed, and `main`
auto-deploys, so that matters.

Consequence to state honestly: at the end of tier 1 the demoted column is still a read
filter. The ticket's "no read filters on it" is met at the END of this roadmap, not at the
end of tier 1.

## Known trap

`sqlc` emits per-query `Row` structs when a query stops selecting a column the table still
has. Keeping `created_by_account_id` while most queries stop reading it can therefore
replace `ManualChargeEntry` with a set of per-query types, and the stale codegen still
compiles. Each tier's `design.md` must say which queries still select the column.
