## Intention

When all three tiers land, the web app is fully bilingual **Spanish (default) / English**:

1. every user-facing string in `internal/gateway` is resolved through a translation
   catalogue instead of being hardcoded English;
2. a **language selector sits top-right in the navbar**, shown with a globe icon plus the
   current language, and switching languages **does not disrupt the current page**;
3. the choice **persists** — in the `accounts.language` column for a signed-in user, and
   in a `lang` cookie for anonymous visitors (login/home), defaulting to **ES** when
   neither is present;
4. the gateway's own instructions require **both EN and ES** for every newly added label,
   so the catalogue cannot silently drift back toward English-only.

## Scope note — why this is a roadmap, not one change

The feature spans **two modules**. `internal/account` owns the persisted preference: the
`accounts` table is its data, so the migration, the sqlc regeneration, and the read/write
port method must live there — no other module may touch that table. `internal/gateway`
owns every user-facing string, the navbar selector, and per-request language resolution,
and it is the only module allowed to produce HTML. Per the proposal rule (multi-module ⇒
roadmap), each module gets its own module-prefixed tier, and the gateway tiers depend on
the account tier for the persistence port.

The gateway work is split into **two** tiers on purpose. Tier 2 is design-bearing — it
decides the catalogue format, how the active language reaches Templ components, and the
htmx swap strategy — and establishes exactly one translated surface as the gold standard.
Tier 3 is then mechanical repetition of that established pattern across the remaining
pages. Separating them keeps the expensive design decisions out of a large mechanical
sweep, and lets tier 3 run on a cheaper model against a settled vocabulary.

## Decisions (binding — settled with the user on 2026-08-13, before any artifact was written)

These were confirmed by the user and are authoritative for every tier's design/spec/tasks.
Tiers MUST NOT reopen them.

1. **The language preference is a column on the existing `accounts` table, NOT a new
   settings table.** `language TEXT NOT NULL DEFAULT 'es'`. Rationale: exactly one
   preference, strictly 1:1 with the account, and it is read on **every page render** — a
   column keeps it on the already-loaded account row with no join on the hot read path,
   which is what the declared read-heavy `Performance-Profile` asks for. A separate
   `account_settings` table was **rejected**: for a single field it buys nothing and costs
   a join or a second query per render, a second sqlc query set, and a "settings row does
   not exist yet" fallback case. Revisit only if per-account preferences genuinely
   multiply (units, timezone, theme) — that is a future change, not this one.
   → tier 1, `RM24-account-add-language-preference`.
2. **Anonymous pages read a `lang` cookie, falling back to `es`.** Logged-out surfaces
   (login, home) have no account row to read, so the cookie is the source of truth there;
   absent cookie ⇒ `es`. The **selector is visible on the login page**, and the cookie
   choice carries into the session at login. For a signed-in user the DB column is
   authoritative and the cookie is kept in sync with it, so the language does not flip at
   the session boundary. → tier 2.
3. **The default language is `es`.** Stated by the ticket. It is the column default, the
   cookie fallback, and the catalogue's base locale.
4. **Supported locales are exactly `es` and `en`.** Any unrecognized cookie or column
   value resolves to `es` rather than erroring — an invalid stored value must never be
   able to break a render.
5. **No re-grill was run.** `openspec/config.yaml` mandates a grill pass on proposals and
   `database` is a built-in design gate, but both gated questions (decisions 1 and 2) were
   put to the user with explicit alternatives and answered immediately before this roadmap
   was written; Step 2's "don't grill when the answer is genuinely obvious" applies. The
   tier-1 migration still faces the **database design gate** before Apply.

### Tier 1 — `[x]` `RM24-account-add-language-preference` (module: `account`)

Add `language TEXT NOT NULL DEFAULT 'es'` to `accounts` via a new goose migration in
`internal/account/db/migrations/` (which is also the single sqlc schema source — keep the
DDL there, never a separate `schema.sql`). Regenerate sqlc. Extend the module's public port
in `service.go` so the gateway can read the value with the account it already loads and
update it when the user switches — without the gateway ever touching the table.

**Index plan: no new index.** The column is never a filter, join, or sort key — it is read
as part of an already-fetched account row keyed by the existing primary key / provider
unique constraint, and written only on an explicit user action. An index would add write
cost and zero read benefit. This must be stated and justified in `design.md`, which is
REQUIRED for this tier (any DB-touching change) and is subject to the **database design
gate** before Apply.

**Proposal prompt:** *"Add a per-account language preference to the `account` module. New
goose migration adding `language TEXT NOT NULL DEFAULT 'es'` to `accounts`; regenerate
sqlc; extend the module's public interface so a consumer can read the current language
alongside the account and persist a change to it. Supported values `es` and `en`, default
`es`; an unrecognized stored value must resolve to `es` rather than error. No index — the
column is never filtered or joined on; justify that in design.md against the read-heavy
performance profile. Non-breaking: existing rows take the default."*

### Tier 2 — `[x]` `RM24-gateway-add-i18n-foundation` (module: `gateway`; depends on tier 1)

The design-bearing gateway tier. Establishes the translation vocabulary and proves it on
one surface end-to-end; it does **not** translate the whole app (that is tier 3).

Delivers: the translation catalogue (format and location inside `internal/gateway` are the
worker's design call, per `ai/go-conventions.md` + `ai/htmx-conventions.md`); per-request
language resolution — DB column for a signed-in account, `lang` cookie for anonymous,
falling back to `es`, with the cookie kept in sync after a signed-in switch; the mechanism
carrying the active language into Templ components without breaking the gateway boundary
or the logic-free-template invariant; the **navbar language selector** (top-right, globe
icon, current language shown) built from the typed `templates/ui/` kit — if no existing
wrapper fits, add one to `ui/` rather than inlining a DaisyUI class; the htmx switch that
changes language **without disrupting the current page**; and the fully translated
**layout/nav shell** as the gold-standard example tier 3 mirrors.

Also delivers the **documentation rule** MAG-8 asks for: update `internal/gateway/AGENTS.md`
(and `README.md` where one exists) to require **both EN and ES** whenever a new user-facing
label is added to any page — worded so a dispatched worker reads it as binding, not
advisory.

**Proposal prompt:** *"Build the i18n foundation in the `gateway` module. Add a translation
catalogue for `es` (default) and `en`; resolve the active language per request from the
signed-in account's `language` column (tier 1's port) or, when anonymous, from a `lang`
cookie, falling back to `es` and treating any unrecognized value as `es`. Keep the cookie in
sync with the DB value after a signed-in switch so language does not flip at login. Carry
the active language into Templ components without violating the gateway boundary or putting
logic in templates. Add a language selector top-right in the navbar — globe icon plus the
current language, composed from the typed `templates/ui/` kit (add a wrapper to `ui/` if
none fits; never inline a DaisyUI component class), visible on the login page too — that
switches language over htmx without disrupting the current page. Translate the layout/nav
shell as the gold-standard surface. Update `internal/gateway/AGENTS.md` to require EN+ES for
every newly added label. Run `make templ && make css` and commit `static/app.css` per the
module CI guard."*

### Tier 3 — `[x]` `RM24-gateway-translate-all-pages` (module: `gateway`; depends on tier 2)

Mechanical sweep applying tier 2's established pattern to every remaining user-facing
string: `templates/pages/` (home, login, dashboard, dashboard_history, charges,
supercharger_stats), `templates/fragments/` (charge forms and rows, charges list, history,
supercharger stats, vehicles, nav header), any user-visible text in `templates/ui/`, and
handler-produced strings such as flash/error messages. Both EN and ES for every key.

The acceptance bar is that **no user-facing English string remains hardcoded** — the tier
must include a check the reviewer can actually run, not a claim.

**Proposal prompt:** *"Translate every remaining user-facing string in the `gateway` module
using the catalogue and language-resolution mechanism established by
`RM24-gateway-add-i18n-foundation`, mirroring the layout/nav shell as the gold standard.
Cover all of `templates/pages/`, `templates/fragments/`, any user-visible text in
`templates/ui/`, and handler-produced flash/error strings. Every key gets both `es` and
`en`. No new design decisions — reuse tier 2's vocabulary. Provide a verifiable check that
no hardcoded user-facing English string remains. Run `make templ && make css` and commit
`static/app.css`."*

## Ordering

Tier 1 MUST land before tier 2: tier 2 calls the account port method tier 1 adds, so
`go build` fails until it exists — that compile error is the intended ordering signal.
Tier 3 MUST follow tier 2: it consumes the catalogue and resolution mechanism tier 2
designs, and mirrors the gold-standard surface tier 2 establishes. All three tiers commit
to the single shared branch `ft/RM24-MAG-8-i18n-translations`.

**Pre-existing in-flight work to watch:** the standalone change
`gateway-battery-consumed-chart` (branch `ft/CH4-gateway-battery-consumed-chart`, status
`proposed`) also touches `internal/gateway/templates/fragments/history*`. It is on its own
branch off a different base, so there is no conflict today, but whichever of the two merges
second will need to translate or rebase the other's strings.
