## Intention

When both tiers land, every registered vehicle carries its two **static** Tesla attributes —
`exterior_color` and `car_type` — on the `vehicles` registry row, captured **once per vehicle**
from the nightly telemetry collector's existing `VehicleData` call (zero extra paid Fleet API
requests). Today those values exist only inside `vehicle_snapshots.raw_data` JSONB, which the
account module cannot read without violating its own boundary. Afterwards the registry read port
(`RegisteredVehicles` / `AllRegisteredVehicles`) surfaces them directly, so any future dashboard
that wants to show the car's model or colour needs no Tesla call and no cross-module access.

## Scope note — why this is a roadmap, not one change

The feature spans **two modules with real work**: `account` owns the `vehicles` table (migration,
domain structs, a new port method, sqlc query), and `telemetry` owns the capture site (the
collector's per-vehicle loop). Per `openspec/config.yaml` (proposal rule: multi-module ⇒ roadmap),
each gets its own module-prefixed tier; the telemetry tier depends on the account port existing.

The `internal/tesla` edit — adding a `VehicleConfigTesla` sub-struct to `VehicleDataTesla` — is
**not** a tier. It is a leaf additive DTO field with no new `VehicleService` method and no
`Raw*`/`explore-tesla-api` surface change, so it is folded into the consuming tier as a granted
path. This follows the just-merged `telemetry-add-tire-pressure-columns` precedent verbatim
(its T1 did exactly this for the TPMS fields). See **RD8**.

This roadmap **adopts and supersedes** the plan doc that previously sat at
`openspec/changes/accout-vehicles-add-static-fields/proposal.md` (note the `accout-` typo, and
that it was a planning note, not a validated OpenSpec change — it had no design/tasks/spec
artifacts). That folder is removed in the same commit that creates this roadmap; its content is
carried forward here and into the tier artifacts.

## Decisions (binding — captured 2026-08-03 with `grill-me`)

These were confirmed by the user and are authoritative for every tier's design/spec/tasks.

1. **RD1 — Capture location: the nightly telemetry collector.** The write-back rides on the
   `tesla.VehicleData(...)` call the collector already makes per vehicle, after the wake flow.
   Zero extra paid Fleet API cost, versus a separate one-shot job. (Pre-resolved in the plan doc
   as its D1.)
2. **RD2 — Write trigger: Go guard + SQL condition (defense-in-depth).** The collector skips the
   port call entirely when the already-fetched `account.OwnedVehicle` has **both** fields non-nil,
   so after the first successful night no `UPDATE` is ever issued. The sqlc query *additionally*
   carries `AND (exterior_color IS NULL OR car_type IS NULL)`, so a partially-written row
   self-heals and a concurrent writer cannot clobber a captured value. `updated_at` moves only
   when a write actually lands. Mirrors RM5's RD2 "belt-and-braces over a microsecond".
3. **RD3 — Field scope: `exterior_color` + `car_type` only.** The live payload carries 47
   `vehicle_config` keys; a curated 7-field "display set" and a full-JSONB column were both
   considered and rejected in favour of strict YAGNI. Further config fields are a separate change.
4. **RD4 — Failure mode: best-effort, counted.** A failed write-back never changes the vehicle's
   `Reason`, never writes a `poll_attempts` row, and is retried for free on the next nightly
   cycle. It increments a new `CycleReport.ConfigCaptureFailures` counter, logged by the
   scheduler — mirroring the existing `ChargingFetchFailures` precedent in the same module, so a
   permanently failing back-fill is visible rather than log-only.
5. **RD5 — Empty string ⇒ skip the write, leave NULL.** The DTO fields are plain `string`. If
   Tesla reports `""` for either value, the collector does **not** call the port: writing an empty
   string would satisfy both the Go guard and the SQL `IS NULL` condition, permanently marking the
   vehicle "captured" with a non-value that can never self-heal. Leaving NULL keeps
   "NULL = not yet captured" literally true and lets the next cycle retry.
6. **RD6 — The port call lives in `collectAccount`, not `attemptVehicle`.** `attemptVehicle`
   returns `(Reason, vehicleConfig)` and stays a pure `[wake→]fetch→map→store` pass that never
   touches `s.acct`; `collectAccount` performs the nil/empty guard, the port call, and the counter
   increment, right beside the existing `record(...)` call. This preserves both existing
   invariants — exactly one capture per vehicle per cycle (retry-safe by construction, since
   `collectVehicle` may call `attemptVehicle` twice), and all account-port access at the level
   where `AccessTokenFor` already lives.
7. **RD7 — Plumb `account.OwnedVehicle` down.** `collectVehicle` / `attemptVehicle` take the
   `OwnedVehicle` they were destructured from instead of separate `accountID` + `teslaID` params
   (a net parameter *reduction*), so the nil-check sits next to the data it tests and future
   registry-driven behaviour needs no further signature churn.
8. **RD8 — The `internal/tesla` DTO addition is a leaf grant, not a tier.** See the scope note
   above; it is task T1 of tier 2.

## Future work

None deferred by this roadmap. Additional `vehicle_config` fields (RD3) and any gateway
**display** of colour/model are separate, not-yet-proposed changes — they are deliberately not
added to `openspec/roadmaps/backlog.md` because no decision here defers committed work; they are
simply out of scope.
