## Intention

When both tiers land, the dashboard "Odometer history" and "Battery history" bar charts:

1. show the **day the data represents** (`EffectiveDate` = `CapturedAt` − 1 day) rather than the
   capture-morning calendar date — fixing the "yesterday's data shown as today" mismatch;
2. format that date as **`MM-DD`** in every tooltip (was `YYYY-MM-DD`), per MAG-6 R1;
3. carry a **`MM-DD` date label under every bar** (adaptive orientation: horizontal for the 6-day
   preset where bars are wide, rotated vertical for 14/30 where bars are narrow), per MAG-6 R2;
4. keep the existing hand-rolled responsive SVG approach (RD7), the existing
   `GET /ui/dashboard/history?days=N` endpoint, the existing days-preset set `[6, 14, 30]`, and the
   logic-free template invariant — the handler pre-computes all label strings + the orientation
   flag, the template only displays.

The platform gains a reusable, self-describing `Snapshot.EffectiveDate` on the telemetry read port
that any future historical consumer (battery-degradation curve, efficiency trend) can use without
re-deriving the offset.

## Scope note — why this is a roadmap, not one change

The feature spans **two modules**: `telemetry` owns the new `EffectiveDate` field on the `Snapshot`
DTO (the day the nightly snapshot represents), and `gateway` owns the tooltip/label presentation
that consumes it. Per the proposal rule (multi-module ⇒ roadmap), each module gets its own
module-prefixed tier change, and the gateway tier depends on the telemetry tier.

## Decisions (binding — captured in the 2026-08-08 grill-me interview with the user)

These were confirmed by the user and are authoritative for every tier's design/spec/tasks.

1. **The "captured_date − 1" adjustment lives on the telemetry DTO, not in the gateway and not in a
   stored DB column.** (Resolves grill-me Q1.) The offset is a property of the data's meaning, not
   presentation; the owning module computes it once so all consumers stay consistent and a future
   consumer can't surface raw `CapturedAt` and diverge. A stored column was rejected as schema
   churn for a cheap read-time derivation; a gateway-only compute was rejected as presentation-locked
   and divergent. → `telemetry-add-effective-date` (tier 1) adds `Snapshot.EffectiveDate`.
2. **The new field is named `EffectiveDate`.** (Resolves grill-me Q2.) Alternatives `SummaryDate`,
   `CoverageDate`, `ReportedDate` were rejected — `EffectiveDate` cleanly separates "when we read
   it" (`CapturedAt`) from "which day it effectively describes" and doesn't lock the name to the
   history-graph use case.
3. **The backend field is a full `time.Time`, NOT pre-formatted.** (Resolves grill-me Q3.) The user
   confirmed the backend keeps the same datetime object shape as `CapturedAt` (including the year);
   the `MM-DD` format is a cosmetic/UI concern owned by the gateway. So tier 1 only derives the
   value; tier 2 owns the `MM-DD` formatting.
4. **The tooltip and the per-bar label both use `EffectiveDate` as `MM-DD`.** Showing the label from
   `EffectiveDate` and the tooltip from `CapturedAt` would re-introduce the 1-day mismatch MAG-6
   specifically fixes — both use `EffectiveDate` for consistency.
5. **Per-bar label orientation is adaptive: horizontal for the 6-day preset, vertical for the 14-
   and 30-day presets.** (Resolves grill-me Q-labels.) The handler decides orientation from the
   preset and exposes a single chart-level `LabelVertical` flag; the template reads only the flag
   (no `days` comparison, no rotation math in markup). This is the "Might be good to put the label
   in vertical way somehow" the ticket hints at, while keeping the 6-day view readable.
