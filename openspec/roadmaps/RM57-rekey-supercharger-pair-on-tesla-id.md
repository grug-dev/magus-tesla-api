# RM57 — Re-key the Supercharger pair on tesla_id

Source ticket: MAG-67 — https://linear.app/magus-monitor/issue/MAG-67/4-re-key-the-supercharger-pair-on-tesla-id-reshape-the-mirror
Parent: MAG-63 (step 4 of 7). Blocker MAG-66 (the authorization seam) is done.
Generated by: `kkpa-dev-harness-pipeline`, from `kkpa-pickup-linear-ticket MAG-67`.

Unit tests: **included** — updated, not new. Tests that assert on `account_id` move to
`tesla_id`. The ticket says so directly.

## Why

Both Supercharger tables are keyed on `account_id`. That is wrong for data about a car.
`account.vehicles` already says which vehicles a user may see. This roadmap removes
`account_id` from both tables and keys them on `tesla_id`.

## The decision that sets the scope

`tesla_id` becomes `NOT NULL` on both tables.

Nothing except `account_id` ties a `telemetry.supercharger_history` row to an account.
`vin` only reaches an account through `account.vehicles`, and that lists **registered**
vehicles only. So once `account_id` is dropped, a row with `tesla_id IS NULL` — an
"orphan" — can never be read again by any query. Keeping the column nullable would not
save it. It would only store rows nobody can reach.

The owner chose `NOT NULL`. The consequence is a real behaviour change, not just a schema
change: `collectChargingHistory` currently writes `tesla_id = NULL` when a session's VIN
is not a registered vehicle (`internal/telemetry/service.go:348`). It must now skip that
session instead. Tesla's charging-history API still returns it, but we stop storing it.

This reverses what MAG-63 wrote for these two tables ("key on `vin`") and what
`20260906000002_add_mirror_watermarks.sql` says in its own comment about orphan recovery.
Both are corrected by this roadmap, not ignored.

Row counts checked before the choice: `telemetry.supercharger_history` has **0** rows with
`tesla_id IS NULL`, and `charging.supercharger_sessions` has **0**. The migration still
deletes such rows first, as a guard for any row that appears before it runs. On the
owner's database today it deletes nothing. The down-migration cannot bring a deleted row
back — it is gone.

## Facts already checked — do not re-derive

- `telemetry.SuperchargerHistoryReader` already has
  `SuperchargerHistoryByVehicleUpdatedSince` (`internal/telemetry/telemetry.go:588`,
  `reader.go:193`). Tier 3 drops its `accountID` parameter. It does not need a new method.
- `authorizeVehicle` exists at `internal/gateway/handlers/handlers.go:1061` and has no
  caller. Tier 4 is its first user.
- The "11 call sites" this roadmap first claimed for `supercharger.go` is **stale**. Tier 2
  collapsed them. Today there are three port calls — `supercharger.go:180`, `:305`, `:681` —
  fed by three `resolveSelectedVehicle` calls at `:145`, `:175`, `:675`.
- `internal/analytics` cannot build a `vehicleref.Ref`. `make vehicleref-guard` allows
  `vehicleref.Authorize`/`.All` only inside the gateway's `authorizeVehicle`. So the three
  `ListSessionsByVehicle*` read ports, which analytics calls at `recalculate.go:158`, `:279`
  and `reader.go:141`, cannot be retyped. `VerifySession` can — the gateway is its only caller.
- The charging index is `idx_supercharger_sessions_vehicle_stop` today, renamed by
  `internal/charging/db/migrations/20260902000003_move_charging_to_own_schema.sql:32`.
  The telemetry index names in the ticket are correct.
- `internal/analytics` also reads the charging session ports (`reader.go`,
  `recalculate.go`). The ticket does not mention it. Tier 3 covers it.
- MAG-63's index rule binds every tier: a `UNIQUE (a, b)` constraint already builds a
  btree that serves equality on `a`, point lookups, range scans on `b` inside one `a`,
  and `ORDER BY b DESC`. Do not add an index that constraint already covers. Justify
  every index against a query that exists today.

## Done when

Neither Supercharger table has `account_id`. `tesla_id` is `NOT NULL` on both. The mirror
runs one pass per `tesla_id`. `VerifySession` cannot be called without a `vehicleref.Ref`,
so the Supercharger write path proves ownership at compile time, not only at run time.
