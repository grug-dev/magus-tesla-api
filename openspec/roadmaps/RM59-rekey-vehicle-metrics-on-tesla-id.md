## Why

`analytics.vehicle_metrics` is the table that started MAG-63. It holds one row per car per
day: battery level, odometer, distance, consumption. All of that describes a **car**, not
an account. But the table is keyed on `(account_id, tesla_id, metric_date)`.

`analytics.vehicle_metric_watermarks` has the same problem. It is the cursor the nightly
cycle uses to know how far it has already derived. One writer owns both tables, in one
transaction, so they move together.

This tier goes last because it is downstream of everything else. `Recalculate` derives its
numbers from three sources: vehicle snapshots, Supercharger sessions, and manual charge
entries. All three had to become car-keyed first, or `Recalculate` would still need an
`accountID` to reach them. MAG-65, MAG-67 and MAG-68 did that.

## Facts already checked — do not re-derive

Measured on the dev database, 2026-09-14. Read-only queries; no DDL was run.

- `analytics.vehicle_metrics`: 120 rows, **0 duplicate `(tesla_id, metric_date)` groups**,
  1 account, 2 distinct `tesla_id`, no NULL `tesla_id`.
- `analytics.vehicle_metric_watermarks`: 4 rows, **0 duplicate `(tesla_id, source)`
  groups**, no NULL `tesla_id`.
- So the collapse step deletes **zero rows** here. It still belongs in the migration, for
  the same reason MAG-65's migration kept its own collapse: safety on a database that was
  migrated before the Go change deployed.
- `tesla_id` is **already `NOT NULL`** on both tables. No `SET NOT NULL` is needed. This is
  unlike RM57, where the column was nullable and NULL rows had to be deleted first.
- The three indexes to replace, exactly as the database reports them today:
  - `vehicle_metrics_account_tesla_date_unique` — `UNIQUE (account_id, tesla_id, metric_date)`
  - `idx_vehicle_metrics_latest` — `(account_id, tesla_id, metric_date DESC)`
  - `vehicle_metric_watermarks_account_tesla_source_unique` — `UNIQUE (account_id, tesla_id, source)`
- **`idx_vehicle_metrics_latest` must survive the re-key as `(tesla_id, metric_date DESC)`.**
  It is not made redundant by the new `UNIQUE (tesla_id, metric_date)`. The reason is in the
  query: `LatestVehicleMetricsByAccount` orders by `tesla_id ASC, metric_date DESC`. That
  mixed direction cannot be served by an all-ascending index in one scan, so dropping the
  DESC index reintroduces the incremental sort it was added to remove.
- No migration in another module reads `analytics.vehicle_metrics.account_id`. Three files
  outside `internal/analytics` mention `vehicle_metrics`, and all three mentions are
  comments.
- `internal/analytics` does **not** import `internal/vehicleref` today. Tier 1 adds the
  first import.
- `ownedVehicles` already exists at `internal/gateway/handlers/handlers.go:1082`. It returns
  `([]vehicleref.Ref, []account.Vehicle, bool)`. Tier 2 does not need a new helper.
- `authorizeVehicle` is at `internal/gateway/handlers/handlers.go:1061`.
- `make vehicleref-guard` allows `vehicleref.Authorize` and `vehicleref.All` only inside
  `internal/vehicleref`, in `_test.go` files, and in the gateway's `authorizeVehicle`.

## Migration order — checked, and it holds

MAG-65 deliberately did **not** drop `telemetry.vehicle_snapshots.account_id`. It only made
the column nullable. The reason is recorded in that migration: the analytics backfill
`20260908000002_add_tpms_pressure_columns.sql:82` joins the two tables with
`WHERE vm.account_id = vs.account_id`, and `MIGRATIONS_DIRS` applies whole module folders in
order — account, telemetry, charging, analytics. Dropping the telemetry column would break
that analytics migration on every fresh database, including each test container. MAG-76 owns
fixing the ordering and is still in Backlog.

**RM59 is safe in both orderings**, and this was verified rather than assumed:

- Applied per module directory (today's `make migrate-up`): the new analytics migration has
  the highest version in its own folder, so it runs *after* `20260908000002`. The backfill
  still sees `vm.account_id`.
- Applied in global version order (what MAG-76 would change it to): the new migration is
  still dated later than the backfill. Same result.

So RM59 does not depend on MAG-76, and does not make MAG-76 harder. This paragraph exists
because "I did not think about the Makefile" is not the same finding as "the Makefile is
unaffected", and only the second one is worth writing down.

## Decisions settled with the owner before any artifact was written

| # | Decision | Why |
|---|---|---|
| RD1 | Two tiers: `analytics`, then `gateway`. The `internal/app` and gateway call-site updates are folded into tier 1 as leader-owned integration. | Mirrors RM57 tier 2, which folded its call-site updates in for the same reason: a tier that changes a port signature must also fix its callers, or it lands with a red build. |
| RD2 | MAG-71's work is part of tier 1. | MAG-71 was cancelled *because* MAG-69 covers it. Leaving it out would drop `account_id` while three queries still filter on it. |
| RD3 | `recalculateAnalytics` dedupes its vehicle loop by `tesla_id`. | `AllRegisteredVehicles` returns one row per (account, vehicle) pair and applies no election. Once `Reconcile` is keyed on the car, a car under two accounts would run the whole reconcile twice with identical arguments. |
| RD4 | `LatestMetricsByAccount` becomes `LatestMetricsForVehicles(ctx, refs []vehicleref.Ref)`. | This is the one port whose `WHERE account_id` filter disappears. A `[]int64` would move that trust from SQL to the caller, where a bug leaks another account's car. A `Ref` can only be built by `authorizeVehicle` or `vehicleref.All`, so the compiler enforces what the filter used to. |
| RD5 | The three chart ports keep `teslaID int64`. | `internal/app/processor.go` calls `ConsumedByDay` and is a background job with no signed-in user, so it cannot build a `Ref`. Its two siblings stay `int64` to keep the set uniform — `buildHistoryView` calls all three side by side. Matches RM57, which kept the three `ListSessionsByVehicle*` read ports on `int64`. |

RD4 and RD5 together set the rule for this roadmap: **a `Ref` guards the read whose account
filter is being removed; the per-vehicle reads that already prove ownership upstream keep
`int64`.**
