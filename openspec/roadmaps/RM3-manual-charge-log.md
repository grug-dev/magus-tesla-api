# Roadmap — RM3-manual-charge-log

**Intention:** every connected user can **manually log a charge session** that Tesla's
Fleet API cannot attribute to their vehicle — home / work / third-party AC or DC
charging — capturing date, energy added, and cost (COP), plus optional battery
before→after, timing, charging type and location. This is the **user-asserted**
complement to the automatic, Supercharger-only sessions RM2 already collects: together
they give a complete per-vehicle charging picture, with zero guessing about ownership.

Generated by the **kkpa-dev-harness-pipeline** (leader session, 2026-07-18) from the
user's request:

> ok, let's go for a manual entry approach ... I want this approach lives in its own
> package/module isolated of the other ones. It does not consume any tesla's fleet api ...
> create the openspec proposal for this new module package, and separate the task/roadmap
> tiers by frontend and backend changes. Help me to design the database table ...

**Why manual entry (not the Tesla energy API):** the Fleet API's Wall Connector energy
history (`GET /api/1/energy_sites/{id}/telemetry_history?kind=charge`) is **charger-centric,
not vehicle-centric** — each session is keyed only by the connector's `device_id`/`din`,
carries **no VIN / vehicle_id**, and in a multi-tenant platform cannot be reliably
attributed to any specific owned vehicle (a second car, guest, or neighbor on the same
connector is indistinguishable). That API was evaluated and **declined** on 2026-07-18 —
see `openspec/roadmaps/backlog.md` (BRAINSTORMING). Manual entry flips the problem: the
**user asserts** which vehicle a session belongs to, so there is nothing to infer.

## Decisions (leader interview, 2026-07-18 — binding for every tier's proposal)

- **New isolated module `internal/manualcharge`** — table `manual_charge_entries`, domain
  type `manualcharge.Entry`, public ports **Writer** (Create / Update / Delete) and
  **Reader**. It owns its own schema under `internal/manualcharge/db` and exposes only Go
  interfaces (module boundaries are sacred).
- **Consumes NO Tesla Fleet API** — 100% user-typed data. The module never imports
  `internal/tesla`, needs no OAuth scope, and wakes no car.
- **Multi-tenant scope, no cross-module FK.** Every row carries `account_id` +
  `tesla_id` + `vin` (the durable vehicle key, mirroring `supercharger_sessions`). No FK
  into the account module's tables (that coupling is forbidden — `ai/architecture.md §2`);
  referential integrity is upheld by flow — the gateway resolves the chosen vehicle from
  **the user's own registered vehicles** (via the `account` port) before calling Writer.
- **Required fields (user):** `charged_on` (DATE), `energy_added_kwh`
  (`NUMERIC(6,2)`, > 0), `price` (`NUMERIC(14,2)`, ≥ 0) + `currency` (`TEXT`, default
  `'COP'`).
- **Optional fields (user):** `started_at`, `ended_at` (TIMESTAMPTZ), `start_battery_pct`,
  `end_battery_pct` (`SMALLINT`, 0–100), `charging_type` (`TEXT`, `AC`|`DC`),
  `location_kind` (`TEXT`, `HOME`|`WORK`|`OTHER`), plus suggested `location_label` (free
  text, esp. for OTHER) and `notes`.
- **This table is MUTABLE** (`updated_at`, supports UPDATE/DELETE) — unlike the
  append-only `vehicle_snapshots` / `poll_attempts`. Hand-typed data needs correction, so
  the Writer port is full CRUD.
- **Enums as `TEXT` + `CHECK`** (not Postgres `ENUM` types) — matches the codebase
  (`billing_type TEXT`, `outcome TEXT`) and is trivial to evolve in a migration. Money is
  `NUMERIC` (never float); energy is native `kWh` (the miles→km rule is distance/speed
  only, so no `Km()` companion applies).
- **Read paths → indexes:** per-vehicle history `(account_id, tesla_id, charged_on DESC)`
  and account-wide history `(account_id, charged_on DESC)`, mirroring
  `supercharger_sessions`. `account_id` leads both (multi-tenant convention); `charged_on
  DESC` matches the "newest first" ORDER BY with no sort step. Fits the read-heavy profile.
- **Frontend lives in `gateway`, by rule.** "No HTML outside `internal/gateway/`" — so the
  isolated `manualcharge` module stays pure backend/storage/domain, and the **gateway**
  grows the htmx page that consumes its ports. That is why Tier 2 is a `gateway` change,
  not a second file in the new module.
- **Autopilot:** ON (default). Tiers advance automatically; the Tier-1 database design gate
  and any review round still pause for the user. Say "one tier at a time" to opt out.

## Future work (recorded, not tiers)

  vehicle's own `charge_energy_added` deltas + `charging_state` transitions (which are
  unambiguously the vehicle's own telemetry, no attribution problem), to pre-fill or
  suggest manual entries. Requires finer-than-nightly polling. Recorded in
  `openspec/roadmaps/backlog.md` (Pending to be picked up). This is the automatic
  counterpart to RM2's "charge-session detector" future note.
