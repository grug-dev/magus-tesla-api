# history-date-range — Dashboard history date-range filters (Linear MAG-7)

## Intention

When both tiers land, the dashboard "Odometer history" and "Battery history" bar charts:

1. are driven by **`GET /ui/dashboard/history?start=YYYY-MM-DD&end=YYYY-MM-DD`** (calendar-day
   range, `end` inclusive) instead of the opaque `?days=N` count param;
2. render a **fixed `[start..end]` date axis** — one bar per calendar day, identical labels on
   both charts — so the odometer chart no longer sits one snapshot-step ahead of the battery
   chart (the MAG-7 mismatch: odometer `days+1` points vs battery `days` points);
3. keep the existing 6/14/30 preset selector, but each preset button now carries a
   server-rendered absolute `start`/`end` (computed at render time: `today-N` .. `today`),
   so the **convention** — *every date-filtered gateway HTTP endpoint takes `start`/`end`
   calendar dates, never a `days` count* — is followed by the only endpoint that exists today
   and discoverable for every future one;
4. carry no "Refresh" button on the dashboard page (a vestigial full-page reload already
   superseded by the `#dashboard-content` / `#dashboard-history` htmx self-refresh);

while preserving the existing hand-rolled responsive SVG charts (RD7), the logic-free template
invariant (the handler pre-computes all bars/labels; the template only displays), and the
`GET /ui/dashboard/history` endpoint identity.

## Scope note — why this is a roadmap, not one change

The feature spans **two modules**: `telemetry` owns the new bounded-window read port
`SnapshotsByVehicleBetween(ctx, uid, teslaID, start, end)` on `telemetry.Reader`, and
`gateway` owns the HTTP param contract, the fixed-axis rendering, the preset rewrite, the
Refresh removal, and the convention doc. Per the proposal rule (multi-module ⇒ roadmap), each
module gets its own `RM8-`-prefixed tier change, and the gateway tier depends on the
telemetry tier.

### Cross-roadmap dependency

RM8 tier 2 (gateway) modifies `internal/gateway/handlers/history.go` and
`internal/gateway/templates/fragments/history.templ` — the **same files** targeted by the
still-unimplemented **RM7 tier 2** `gateway-history-graph-labels-tooltips` (MAG-6, the date
*display* fix). RM8 tier 2 **depends on RM7 tier 2 being applied first**; implementing them
out of order on the same handler will produce a conflicting merge. RM8 tier 1 (telemetry
`Between` port) has **no** such dependency and can start immediately after RM8's roadmap
artifacts exist. (See "Ordering" below.)

## Decisions (binding — captured in the 2026-08-09 grill-me interview with the user)

These were confirmed by the user and are authoritative for every tier's design/spec/tasks.

1. **Add `SnapshotsByVehicleBetween(start, end)` to the telemetry Reader port** (resolves
   Q1). The convention named by the ticket ("date filters on APIs should be handled by
   start/end date filters") is treated as covering the internal Go read port too, not only
   the HTTP surface — so the bounded-window read is a first-class telemetry method. Rejected:
   keeping `SnapshotsByVehicleSince` and clamping the upper end in the gateway (would have
   kept the change single-module, but leaves the port open-ended and makes the convention
   less honest). → `RM8-telemetry-between-range-port` (tier 1).
2. **HTTP date params: `?start=YYYY-MM-DD&end=YYYY-MM-DD`**, both whole calendar days, **`end`
   inclusive**, default 6-day window (`today-6`..`today`) when absent. Validation: `400` on
   malformed non-ISO dates; clamp `end >= start` and `end <= today`; **hard cap the window at
   ≤ 90 days** (400 on a wider request) to protect the hot read path from an unbounded range
   scan (Performance-Profile: read-heavy). Rejected: datetime-with-`Z` (midnight
   mis-bucketing), no window cap (unbounded read).
3. **The date selector UI keeps the 6/14/30 preset buttons** (resolves Q3) — the gateway
   view-model computes `start = today-N`, `end = today` at render time and the templ emits
   `?start=...&end=...` per preset. No client JS, no `<input type=date>`; identical UX to
   today. A custom calendar picker is out of scope (no ticket ask; would break the
   "no client JS" gateway invariant) and would be its own change.
4. **Fixed `[start..end]` date axis, one bar per calendar day, identical on both charts**
   (resolves Q4). Missing-day bars render as **empty slots that retain their date label** so
   the axes align even when a night's snapshot is absent. Odometer needs one snapshot before
   `start` for its first delta, which the gateway supplies via a **1-day lookback** — it
   passes `readStart = start - 1 day` to `SnapshotsByVehicleBetween` but only **displays**
   bars for `[start..end]`. The lookback is a gateway concern; the port stays a clean
   `Between(start, end)`. This is the real fix for the MAG-7 "odometer 08-01 / battery 08-02"
   offset, which stems from odometer's `days+1` snapshots vs battery's `days` snapshots under
   the old count-based scheme — the fixed axis removes the per-snapshot-shift behavior.
5. **Remove only the dashboard page Refresh button** (`pages/dashboard.templ`), a plain
   `Href:"/dashboard"` page reload already superseded by the `#dashboard-content`
   (`vehicle-changed`) and `#dashboard-history` (preset click) htmx self-refresh (resolves
   Q5). The **charges-list** Refresh (`fragments/charges_list.templ`) belongs to a different
   feature (manual charge records) and stays.
6. **The convention's canonical home is `internal/gateway/AGENTS.md`** (the module owning all
   HTTP endpoints, already in every gateway worker's doc-pack), with a **one-line pointer in
   `ai/go-conventions.md`** for cross-cutting discoverability (resolves Q6). Rejected: CLAUDE.md
   always-loaded (unjustified context cost for a single-module convention), module-only (not
   found by agents who never read the gateway AGENTS.md).

## Ordering

1. **Tier 1 (telemetry `Between` port) is unblocked and may start immediately.** It touches
   only `internal/telemetry/` and has no same-files conflict with RM7.
2. **Tier 2 (gateway) depends on:** (a) tier 1 landing (it imports
   `SnapshotsByVehicleBetween`); and (b) **RM7 tier 2 `gateway-history-graph-labels-tooltips`
   being applied first**, because both modify `history.go` and `history.templ`. Implementing
   RM8 tier 2 before RM7 tier 2 produces a conflicting merge on the same handler — the
   compile/test break is the intended ordering signal, but a manual merge-resolution would
   still be required, so apply RM7 tier 2 first.

Both tiers commit to the single shared `ft/RM8-history-date-range` branch.
