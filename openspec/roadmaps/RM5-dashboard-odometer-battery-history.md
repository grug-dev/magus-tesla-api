> **Date:** 2026-07-29

## Intention

When both tiers land, the dashboard's two "Odometer history" and "Battery history" bento cards —
today honest `dashHistoryEmpty()` placeholders — render **real, responsive bar charts** for the
selected vehicle over a user-chosen window (default **6** days, presets 6 · 14 · 30). Odometer
bars show **km driven per day** (km, per the mandatory miles→km rule); battery bars show
**battery level %**. Changing the day count re-fetches both charts from a single new gateway API
endpoint. The charts are server-rendered SVG (no JS chart dependency), so the platform gains a
reusable per-vehicle history read port that every future historical feature (battery-degradation
curve, efficiency trend) consumes without re-touching telemetry.

## Scope note — why this is a roadmap, not one change

The feature spans **two modules**: `telemetry` owns the per-vehicle history **read port**, and
`gateway` owns the **API endpoint, the charts, and the days control**. Per `openspec/config.yaml`
(proposal rule: multi-module ⇒ roadmap), each module gets its own module-prefixed tier change; the
gateway tier depends on the telemetry port existing.

Tier 1 (`telemetry-add-snapshot-history-read-port`) already existed as a standalone proposal
(created in the 2026-07-28 dashboard-port review, which named this follow-on `apex-dashboard-
history-charts`). This roadmap **adopts that existing change as tier 1** (completing its
design/tasks/spec) rather than creating a duplicate, and renames the follow-on to the
module-prefixed `gateway-dashboard-history-charts` (tier 2).

## Decisions (binding — captured in the 2026-07-29 brainstorm with the user)

These were confirmed by the user and are authoritative for every tier's design/spec/tasks.

1. **Window is controlled at the gateway edge, not in the port.** The telemetry port takes a
   `since time.Time`; the gateway computes it from the `days` query param. This is what makes the
   window "easily changeable and sent to the API" — the port stays a pure data accessor and every
   future consumer picks its own window. (Resolves tier-1 open question **D1**.)
2. **Defense-in-depth `account_id` filter.** The port method takes `accountID` and the query
   filters `account_id = $1 AND tesla_id = $2`, even though the gateway only ever resolves
   `tesla_id` from `account.RegisteredVehicles(uid)`. Belt-and-braces over a microsecond.
   (Resolves **D2**.)
3. **No new index, no migration.** The existing `idx_vehicle_snapshots_vehicle_time
   (account_id, tesla_id, captured_at)` index (ascending `captured_at`) already serves the new
   `account_id = $1 AND tesla_id = $2 AND captured_at >= $3 ORDER BY captured_at ASC` as a forward
   range scan. Tier 1 adds **only a sqlc query + a Reader method** — no DB object changes, so the
   **database design gate does not trigger**. (Resolves **D3**; corrects the original proposal's
   "one new index" assumption.)
4. **Safety `LIMIT` baked into the query** (e.g. `LIMIT 400`) as a guard against an accidentally
   huge result if capture cadence ever increases; the 30-day window already bounds it to ~30 rows.
   (Resolves **D4**.)
5. **Odometer bars = km driven per day (delta).** Each bar height = `OdometerKm(dayN) −
   OdometerKm(dayN-1)` — meaningful varying bars matching the Stitch mock, not near-flat cumulative
   odometer. To render **N** delta bars the gateway fetches **N+1** snapshots (one before the first
   shown day seeds the first delta); the `days` selector value = number of bars. Each bar's native
   SVG `<title>` tooltip shows date + km driven that day + the cumulative odometer reading.
6. **Battery bars = battery level %** (absolute 0–100, not a delta); tooltip shows date + level% +
   rated range km.
7. **Rendering = hand-rolled responsive SVG, no chart library.** Templ generates the SVG (`viewBox`
   + `width:100%` scales natively; native `<title>` tooltips). Zero JS dependency, no build step —
   best fit for the Node-less stack + simple bars, and the most AI-efficient (no vendored asset,
   fully server-rendered). The handler pre-computes all bar heights and tooltip strings (no math in
   templates). **The alternative — a vanilla-JS chart library (uPlot/Chart.js) — is rejected for
   now** as unjustified weight for simple bars; if a future chart outgrows SVG, that reversal is an
   architecture decision that must be recorded per Decision 8.
8. **Important library/architecture decisions update the module `AGENTS.md` in the same change.**
   Tier 2 records the "hand-rolled SVG, no chart lib" decision in `internal/gateway/AGENTS.md` and
   adds a standing convention line: *any decision to add/replace a client-side library or change a
   rendering/architecture approach MUST be recorded in the owning module's `AGENTS.md` as part of
   the same change.* (User's explicit ask.)
