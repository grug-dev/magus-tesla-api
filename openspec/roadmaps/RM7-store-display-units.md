# RM7 — Store display units in `vehicle_snapshots` (convert on write, not on read)

> **Generated by skill:** `opsx:propose` → authored as OpenSpec artifacts by the session leader
> (Claude Code). The multi-module split follows `openspec/config.yaml` (proposal rule: a change
> spanning modules becomes a roadmap with one module-prefixed change per tier).
> **Originating user prompt:** *"The vision of this project is to be faster in read, slow in
> writes. So, if we are doing data transformations for unit of measures when reading them...
> that's not good. right? So, I'd like to move the logic of those conversions when writting them
> into the vehicle snapshots to have the distance units as `km`, the temperature units as `C` and
> the tire pressure as `Psi`. Also, rename the affected core columns of the vehicles snapshots to
> add a suffix with the unit of measure. (e.g. XXX_km, XXX_psi, etc). No conversions should be
> done when reading data. (Thousand separator is something on the UI scope, that's good.. but the
> value should be without it)"*
> **Date:** 2026-08-06

## Intention

When all four tiers land, `vehicle_snapshots` stores **display units** — kilometres, Celsius, PSI —
under column names that **carry their unit as a suffix** (`odometer_km`, `inside_temp_c`,
`tpms_pressure_fl_psi`, `charger_power_kw`, …). The nightly poller converts once, at write time.
**No read path performs arithmetic**: the gateway dashboard, the history charts, and the battery
efficiency derivation all read plain fields off `telemetry.Snapshot`. Unit conversion stops being
a per-render cost paid on every dashboard load and becomes a once-per-vehicle-per-night cost paid
by a poller that runs at midnight.

Two structural wins ride along. The schema stops hiding units behind migration comments — an agent
reading `odometer_km` never has to look up what `odometer` meant. And after tier 1, **every unit
conversion in the codebase lives in exactly one module**, `internal/tesla`, the vendor adapter that
owns the API-native DTOs; `internal/telemetry` ends up with zero conversion constants.

## Scope note — why this is a roadmap, not one change

The change spans **four modules**: `tesla` owns the conversion companions, `telemetry` owns the
table and the write path, and `battery` + `gateway` are the consumers that call the read-time
companions today. Per `openspec/config.yaml` (proposal rule: multi-module ⇒ roadmap), each module
gets its own module-prefixed tier change. The `kkpa-dev-harness-pipeline` sandboxes each worker to
exactly one child of `internal/`, so a single four-module change could not be dispatched at all.

**This roadmap differs from RM1–RM6 in one important way: it is a breaking rename, not an additive
feature.** Tier 2 renames `Snapshot.Odometer` → `Snapshot.OdometerKm` and deletes the companion
methods, which stops `internal/battery` and `internal/gateway` from compiling until tiers 3 and 4
land. That is expected and accounted for — see Decision 8.

## Decisions (binding — captured in the 2026-08-06 session with the user)

These are authoritative for every tier's design/spec/tasks.

1. **Conversion moves from read time to write time.** `CLAUDE.md` → *Performance-Profile:
   read-heavy — read performance is mandatory over write performance; writes are mostly done by
   pollers at midnight, so denormalizing, indexing aggressively, and precomputing for reads is
   acceptable*. Today every read converts: `telemetry.go:110-155`, `battery/derive.go:32,54-55`,
   `gateway/handlers/handlers.go:311,313,400,405`, `gateway/handlers/history.go:147,154,196` —
   the last one once per chart bar per render. Writes happen once nightly per vehicle. The
   conversion belongs on the write side.

2. **Every unit-bearing column gets a unit suffix**, including columns whose value does not change
   (temperature is already Celsius; percentages, kWh, kW, V and A are already API-native). One
   consistent rule an agent never has to look up beats a smaller diff. Columns that carry no unit
   are untouched: `id`, `account_id`, `tesla_id`, `captured_at`, `captured_date`, `updated_at`,
   `raw_data`, `charging_state`, `locked`, `sentry_mode`, `car_version`, and
   `max_range_charge_counter` (a count, not a unit).

3. **Existing rows are converted by in-place arithmetic in the migration** — `ALTER TABLE …
   RENAME COLUMN` for all 15, then one `UPDATE` multiplying the 6 value-changing columns.
   Rejected: re-deriving from `raw_data`, which is a much heavier JSONB extraction per row per
   column and would write NULL for any row whose payload lacks the path — losing data the typed
   column still holds.

4. **Scope is `vehicle_snapshots` only.** `supercharger_sessions` already stores `energy_kwh`
   (suffixed) and `total_cost` (paired with a `currency` column) and holds no miles or bar, so it
   has nothing to convert. `internal/manualcharge` is a separate module and out of scope.

5. **All unit conversion lives in `internal/tesla`.** Tier 1 adds `TpmsPressure{FL,FR,RL,RR}PSI()`
   to `tesla.VehicleStateTesla` and moves the `barToPSI` constant there, joining the existing
   `OdometerKm()` / `BatteryRangeKm()` / `ChargeRateKmh()` / `SpeedKmh()` companions. Tier 2's
   `snapshotFrom` then calls those companions instead of doing arithmetic, and `internal/telemetry`
   drops both `milesToKm` and `barToPSI`. **Rejected:** keeping `barToPSI` inside telemetry and
   converting inline — one fewer tier, but conversion logic in two modules, so an agent has two
   places to look.

6. **Domain field names absorb the suffix and the read companions are deleted.**
   `Snapshot.Odometer` → `Snapshot.OdometerKm float64` **collides** with the existing
   `OdometerKm()` method, so deleting the six methods at `telemetry.go:110-155` is required for the
   package to compile — not optional cleanup. Same for `BatteryRange` → `BatteryRangeKm`,
   `InsideTemp` → `InsideTempC`, `TpmsPressureFL` → `TpmsPressureFLPSI *float64`, and the
   percent / kWh / kW / V / A fields.

7. **`raw_data` remains the lossless record.** Storing converted kilometres means the original
   miles value is no longer bit-exactly recoverable from the typed column. Accepted: the full
   API-native payload is still in `raw_data`, so nothing is destroyed and any row can be
   re-derived retroactively.

8. **The tree does not build between tier 2 and tier 4, and that is planned.** Tier 1 is additive
   and compiles standalone. Tier 2 breaks `internal/battery` and `internal/gateway` by
   construction. Tiers 3 and 4 restore the build. Tiers 2–4 must land on the same branch before
   the roadmap can be called done; **do not archive tier 2 on the assumption `go build ./...`
   passes** — its own verification is scoped to `go build ./internal/telemetry/... ./internal/tesla/...`
   plus that module's tests, with the full-tree build deferred to tier 4's gate.

9. **The `database` design gate triggers on tier 2.** Per `CLAUDE.md` → Design-Gates, the
   migration and index plan need the user's explicit confirmation before Apply. The gate is
   expected to be quick: every rename is on a non-indexed column or on a column that appears in no
   index, so `vehicle_snapshots_account_tesla_date_unique` `(account_id, tesla_id, captured_date)`
   and `idx_vehicle_snapshots_vehicle_time` `(account_id, tesla_id, captured_at)` are untouched and
   **no index is rebuilt**.

10. **Formatting stays in the gateway; the value stays numeric until it gets there.** `formatKm`
    (`gateway/handlers/handlers.go:425`) survives — rounding and thousands-grouping are
    presentation, exactly as the user asked. What it must not do any more is convert. The stored
    column and the domain field are plain unformatted numbers.

11. **The conventions that mandate the old pattern are re-scoped, not silently violated —
    but by a separate change.** `ai/go-conventions.md:44-47` and the matching `CLAUDE.md`
    non-negotiable currently require a `<Field>Km()` companion for *every* miles field. Both are
    rewritten to: *adapter DTOs mirror the API (miles/bar) and keep `Km()`/`Kmh()`/`PSI()`
    companions; **persisted** domain types store display units under unit-suffixed names,
    converted once at write; no read path converts.*
    **Amended 2026-08-06:** that platform-wide rewrite moved out of tier 2 into
    `platform-unit-of-measure-convention`, which generalises this roadmap's decision to every
    table and every module. Tier 2 keeps only its module-local `internal/telemetry/AGENTS.md`
    edit, so one rule has exactly one owner and no two changes edit the same lines. There is no
    apply-order dependency between them, but that change is archived **after** tier 4 — until
    then `vehicle_snapshots` is the one table that does not yet comply.

12. **Nil fidelity stays where it already lives — in `telemetry`, not in the adapter.** The
    adapter's `VehicleStateTesla.TpmsPressure{FL,FR,RL,RR}` fields are plain `float64` (the Fleet
    API includes them in `vehicle_state` whenever the vehicle has TPMS sensors), so the tier-1
    companions return plain `float64` like `OdometerKm()` does. The nil/not-reported distinction is
    created one layer up, where `snapshotFrom` pointer-wraps via `ptr()` into
    `Snapshot.TpmsPressure*PSI *float64` — exactly as it does today. Tier 2 converts **before**
    wrapping, so NULL still means "not reported or pre-migration" and a truthful `0.0` is still
    stored non-NULL.

## Verification (roadmap-level, at tier 4)

1. `make sqlc` regenerates cleanly against the renamed columns.
2. `go build ./... && go vet ./... && go test ./...` all pass.
3. `make migrate-up` on a scratch DB, then the `DATABASE_URL`-gated integration tests
   (`internal/telemetry/db_integration_test.go`, `db_read_integration_test.go`,
   `db_sourcea_integration_test.go`).
4. Migration round-trip `up → down → up` returns values to miles/bar and back with no drift
   beyond float tolerance.
5. Spot-check a real row: `odometer_km ≈ 1.609 ×` the pre-migration `odometer`, and the
   `/dashboard` odometer/range tiles render the same numbers as before the roadmap.
6. `grep -rn "OdometerKm()\|BatteryRangeKm()" internal/battery internal/gateway` returns nothing.

## Future work

- **`internal/manualcharge` and `supercharger_sessions` unit-suffix audit.** Deliberately excluded
  by Decision 4 because neither stores a value needing conversion. If a future column in either
  does carry an unsuffixed unit, apply Decision 2's rule to it then — add a backlog item at that
  point, not before.
- **Dashboard vs vehicle-card decimal inconsistency.** `mapDashboardSnapshot` formats whole units
  (`"20,088 km"`, `"22 °C"`) while `mapVehicles` formats one decimal (`"322.0 km"`, `"22.5 °C"`)
  for the same snapshot. Noticed while tracing the read paths for this roadmap; unrelated to units
  and deliberately not folded in. Purely presentational — pick a house style in a separate gateway
  change if it ever bothers you.
