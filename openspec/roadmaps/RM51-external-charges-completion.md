# external-charges-completion — Auto-complete a charge entry and mark a real zero price (Linear MAG-58)

> **Date:** 2026-09-09

## Intention

Three changes to the `/external-charges` page and the module behind it.

1. **An entry completes itself.** Today the only way to finish a charge record is for the user to
   move the status control from `IN_PROGRESS` to `DONE` by hand. After this roadmap, the
   `charging` module promotes the entry itself: if the fields that `DONE` requires are all
   present, the entry is stored as `DONE`, whatever status was submitted.
2. **A zero price says whether it is real.** Today `price` is `NOT NULL`, and an empty price box
   saves as `0`. So a real free charge and a forgotten price look identical. A new
   `price_source` column records which one it is, driven by a "this charge was free" checkbox.
3. **A "last month" date preset.** The filter row gains a third preset next to "last 7 days" and
   "this month".

## Scope note — why this is a roadmap, not one change

The feature spans **two modules**. `charging` owns `manual_charge_entries`, the new column, the
status rule and the write port. `gateway` owns the form, the checkbox and the date presets. Per
the proposal rule (multi-module ⇒ roadmap) each module gets its own module-prefixed tier change.

Only two tiers, and they do not alternate: the gateway tier needs the domain field that the
charging tier adds, so there is no useful screen to show in between.

## Decisions (binding — settled with the user on 2026-09-09, before any artifact was written)

These were confirmed by the user in a `grill-me` interview and are authoritative for every tier's
design, spec and tasks. A tier worker must not re-open them.

### RD1 — The module promotes an entry to `DONE`, and never demotes it

If the submitted status is `IN_PROGRESS` and every field that `DONE` requires is present, the
entry is stored as `DONE`.

**Rule, exactly:**

```
if e.Status == StatusInProgress && missingFields(e as DONE) is empty {
    e.Status = StatusDone
}
```

The test **reuses `missingFields` against `RequiredFieldsFor(StatusDone)`**. It must NOT hardcode
`ended_at` and `end_battery_pct`. `RequiredFieldsFor` stays the single source of truth, so if the
`DONE` set ever gains a field, promotion tightens on its own.

**Promotion only — never demotion.** Nothing in this roadmap moves an entry from `DONE` back to
`IN_PROGRESS`. The user reopens an entry by clearing `ended_at` or `end_battery_pct`, which then
fails the `DONE` required-field check as it does today.

**Known and accepted cost:** a user who submits `IN_PROGRESS` with both fields filled gets `DONE`
saved instead, with no warning. The user chose this knowingly. Do not add a guard, a warning, or
a "keep open" escape hatch.

**Rejected:** deriving the status entirely from the fields and deleting the status control (it
would make RD13's JS toggle dead code and remove user control). **Rejected:** an explicit
"keep open" checkbox (a new field on the wire for a case the user does not want).

### RD2 — The promotion runs on **both** `Create` and `Update`

One helper in `charging`, called from `Writer.Create` and `Writer.Update`. The ticket says
"when updating", but the user chose both, so no write path can produce an entry that is complete
and still open.

**Why:** it makes "complete fields ⇒ status `DONE`" a true invariant of the table, instead of a
rule that holds only if you happen to edit the row afterwards.

### RD3 — A new `price_source` column records whether a zero price is real

Column on `charging.manual_charge_entries`:

```sql
ALTER TABLE manual_charge_entries
    ADD COLUMN price_source TEXT NOT NULL DEFAULT 'UNCONFIRMED'
        CHECK (price_source IN ('USER','UNCONFIRMED'));

UPDATE manual_charge_entries SET price_source = 'USER' WHERE price > 0;
```

**Values and the rule that computes them:**

| Condition | `price_source` |
|---|---|
| `price > 0` | `USER` |
| `price == 0` and the user confirmed | `USER` |
| `price == 0` and not confirmed | `UNCONFIRMED` |

Meaning: `USER` = this amount is real. `UNCONFIRMED` = the zero is probably missing data, not a
real free charge.

**`TEXT` + `CHECK`, not a Postgres `ENUM`** — the same reason
`20260829000002_add_entry_status.sql` gives: `location_kind`, `charging_type`, `status` and
`energy_source` in this table all do it this way, and an enum's value set is painful to change.

**Two statements, not one.** The precedent used a single `ADD COLUMN` because its backfill value
*was* the default. Here it is not — the right backfill depends on each row's `price` — so it
needs the two-step shape of `20260720000001_require_location_kind.sql`.

**`UNCONFIRMED` is the default because it fails closed.** A future insert that forgets the column
then says "nobody vouched for this", which is honest. `USER` as the default would claim the
opposite.

**The backfill is honest, not cosmetic.** A historical positive price was typed by a person, so
`USER` is true. A historical zero was never confirmed, so `UNCONFIRMED` is true — and it surfaces
old rows worth re-checking, the same spirit as the `IN_PROGRESS` backfill of RD1 in RM33.

**Rejected:** a single `price_zero_confirmed_at TIMESTAMPTZ` flag (it records one event instead of
the field's provenance, and does not mirror a pattern the table already has). **Rejected:** making
`price` nullable to separate "blank" from "typed zero" at the root — correct but far larger, and
the user chose the smaller change.

### RD4 — `charging` computes `price_source`; the gateway never sends it

Exactly like `energy_source`, which the KB records as "module-computed, never caller-supplied".

The gateway sends only the user's **intent** — a boolean on the write input, e.g.
`Entry.PriceConfirmed`. `charging` applies the RD3 table and writes the column. A caller-supplied
`price_source` is ignored or rejected; it is never trusted.

**Why:** it keeps the derived column's rule inside the module that owns the data, so the gateway
cannot drift from it.

### RD5 — No index on `price_source`

No query filters or sorts on it. The list read fetches whole rows inside a date window and takes
this column along at no cost. On a two-value column an index would serve no read and tax every
write.

The read-heavy `Performance-Profile` does **not** justify an index that no read uses. If a "show
me unconfirmed zero prices" view is added later, that query is what justifies the index, and it
is added then.

**Rejected at the gate:** a partial index
`ON (vehicle_vin, charged_on) WHERE price_source = 'UNCONFIRMED'`. The user was offered it and
declined.

### RD6 — The confirmation is a plain checkbox, not a prompt

A "this charge was free" checkbox sits next to the price input, on **both** the create form and
the edit row.

**This is a deliberate divergence from the ticket text.** The ticket asked to "prompt the user"
and block until they confirm. A checkbox does not prompt and does not block: a user can save an
unconfirmed zero by simply not looking at it. The user chose this trade knowingly. Do not
"restore" the prompt.

**Consequences, all settled — a tier worker does not re-decide them:**

- The checkbox is **always visible**. Showing it only when the price is zero would need new
  client-side JS, which is exactly what this choice avoids.
- The server **ignores it when `price > 0`**, because that case is always `USER` by RD3.
- The save **never blocks** on it. There is no 422, no confirm panel, no extra round-trip.
- **No new JS.** `internal/gateway/static/app.js` gains nothing. The sanctioned-exception list
  (RD12 date splice, RD13 status-required toggle, RD14 location-label toggle) stays closed at
  three, and no `RD15` is created.

**Rejected:** a server round-trip answering 422 with a confirm panel (correct and JS-free, but
two round-trips and much more code). **Rejected:** a client `confirm()` interceptor (one
round-trip, but a fourth JS exception on a deliberately closed list).

### RD7 — "Last month" is the **previous calendar month**

`prevStart := startOfMonth(today).AddDate(0, -1, 0)`, `prevEnd := endOfMonth(prevStart)`. On
2026-09-09 that is 2026-08-01 to 2026-08-31.

**Why:** it reads as a set beside the existing "this month" preset, and it reuses `startOfMonth`
and `endOfMonth`, which both already exist. No new date maths.

**Rejected:** a rolling last-30-days window. It matches "last 7 days" in style, but it overlaps
"this month" for most of any month, so the two buttons would look redundant.

### RD8 — The preset is added to `/external-charges` only

The ticket says `Page: external-charges`. `/supercharger-stats` keeps its own presets untouched.

## Verified codebase findings (checked before the roadmap; tiers do not re-derive these)

- **`RequiredFieldsFor` and `missingFields` already exist** in `internal/charging/validation.go`,
  and `Writer.Create` / `Writer.Update` in `service.go` already call `normalizeStatus` then
  `missingFields` before any DB call. RD1's promotion belongs in that same sequence — **after**
  `normalizeStatus` and **before** `missingFields`, so the entry is validated against the status
  it will actually be stored with.
- **`price` is `NUMERIC(14,2) NOT NULL CHECK (price >= 0)`** and `charging.Entry.Price` is a plain
  `float64`, not a pointer. This is why blank and zero are the same value, and why RD3 is needed
  at all.
- **The gateway already turns an empty price box into `0`** —
  `internal/gateway/handlers/external_charges.go` (~line 1320): `if raw.Price != ""` else `price`
  stays at its zero value. That behaviour is unchanged by this roadmap.
- **`buildExternalChargesPresets`** in `internal/gateway/handlers/external_charges_range.go`
  builds exactly two `fragments.RangePreset` entries and computes `Active` by exact match against
  each preset's own recomputed window. Adding a third preset is an append to that slice — nothing
  hardcodes a preset count or index. `endOfMonth` is defined in that same file; `startOfMonth` is
  the existing package-level helper in `supercharger.go`.
- **The i18n keys to mirror** are `KeyChargesRangeLast7Days` and `KeyChargesRangeThisMonth` in
  `internal/gateway/i18n/catalog.go` (keys `charges_range.last_7_days` / `charges_range.this_month`).
  The new key follows as `charges_range.last_month`, with both `ES` and `EN` non-empty.
- **`MIGRATIONS_DIRS` order is account → telemetry → charging → analytics.** Tier 1 adds a
  charging migration that touches only its own schema, so the order is not at risk — but tier 1
  must still re-check it and record the result, per `CLAUDE.md`.
- **`make sqlc` must run after the migration.** `price_source` has to reach the generated models
  before any Go code can read or write it.
- **The knowledge base must be corrected in the same tiers.**
  `kkpa/context/workflows/manual-charge-crud.md` documents the status rule, the required-field
  rule and the "price empty ⇒ 0" behaviour; `kkpa/context/input-port/charging/external-charges.md`
  documents the form field set and the date presets. Both go stale with this roadmap. Update the
  INDEX rows for `entry status` and `energy source` too, and add one for `price source`. Never
  touch `openspec/changes/archive/`.
