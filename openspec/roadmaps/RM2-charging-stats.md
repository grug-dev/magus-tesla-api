# Roadmap — RM2-charging-stats ⏳ awaiting live `dx/charging/history` schema

**Intention:** every connected user gets per-vehicle **charging analytics** — richer
nightly charge-state fields **plus** true **charge sessions** (energy added, battery
before→after, efficiency, location/fees where Tesla provides them) sourced from Tesla's
charging-history endpoint, with a one-time historical **backfill**. Built on the EXISTING
nightly poller; users never trigger Tesla API calls.

Generated by the **kkpa-dev-harness-pipeline** (leader session, 2026-07-14) from the
backlog item **CHARGING STATS** (`openspec/roadmaps/backlog.md`):

> I'd like to start fetching nightly charging stats for vehicles ... a nightly snapshot
> of charging events ... store them in a separate table ... analytics on charging
> behavior, energy usage ... backfill the table with historical data ... query the
> battery level before and after charging events, as well as the energy used during the
> charge ... calculate efficiency and other metrics.

## Decisions (leader interview, 2026-07-14 — binding for every tier's proposal)

- **Scope = both sources (A + B):**
  - **A — enrich the nightly snapshot:** promote charge-state fields we ALREADY capture
    in `vehicle_snapshots.raw_data` (`charge_energy_added`, `charger_power`/`voltage`/
    `actual_current`, `usable_battery_level`, `fast_charger_type`, …) into extracted
    columns / a read model. **No new Tesla call** — the history is already in the JSONB.
  - **B — true charge sessions:** add Tesla's `GET /api/1/dx/charging/history` and store
    one row per session in a new `charge_sessions` table, with a first-run **backfill**
    over the paginated history. This is the ONLY source of real per-session energy /
    before→after / efficiency.
- **Owning modules:** the Fleet API call lives in **`tesla`** (only adapters may call
  Tesla — boundaries are sacred); the table + collector + backfill live in **`telemetry`**
  (it already owns nightly collection + append-only storage and the account/tesla ports).
  ⇒ multi-module ⇒ this roadmap.
- **Collection reuses the existing nightly cycle**, but `dx/charging/history` is
  **server-side → no vehicle wake** (cheaper than `vehicle_data`).
- **⛔ Schema gate (see below):** the user will provide the REAL `dx/charging/history`
  response later. The `charge_sessions` table AND the typed `ChargingHistoryTesla` DTO are
  designed **only after** those fields are confirmed — no guessing, **no paid exploration
  call from the assistant**.
- **DB design gate + grill-me deferred:** per `openspec/config.yaml`, the `charge_sessions`
  schema needs a design.md (schema + rationale + index plan vs the read-heavy profile) and
  the proposal must use `grill-me`. That grill happens on the **confirmed** fields, as part
  of Tier 2's design — not before.
- **Autopilot:** OFF — the user is in the loop (provides the response mid-flight); tiers
  advance one at a time.

## ⛔ BLOCKED — awaiting the live `dx/charging/history` response

**Do NOT design or create the `charge_sessions` table, its migration, or the typed
`ChargingHistoryTesla` DTO until the user provides the real Fleet API
`GET /api/1/dx/charging/history` JSON response.** Reason: the Fleet API docs confirm the
endpoint exists and is paginated but do NOT enumerate its response fields (energy? fees?
battery %? site/location? timestamps?). Designing the table/DTO against guessed fields
would be reworked at the database design gate.

**What CAN proceed without the response (schema-independent):**
- Tier 1(a): `ChargingHistoryRaw` (returns `json.RawMessage`, OFF the `VehicleService`
  interface) + `cmd/explore-tesla-api` surface + README — this is also the tool that
  **captures** the response.
- Tier 2(a): Source-A snapshot-column enrichment (those `charge_state` fields are already
  known and already stored).

**What UNBLOCKS on the response:**
- Tier 1(b): typed `ChargingHistory` method + `ChargingHistoryTesla` DTO (+ `…Km()`
  companions for any miles field) designed against the confirmed fields.
- Tier 2(b): `charge_sessions` schema + migration + collector upsert/dedup + backfill,
  designed against the confirmed fields (then through the DB design gate + grill-me).

**Open risks to resolve WITH the response:**
- Does `dx/charging/history` include home / third-party AC charging, or only
  Tesla-network / Supercharger sessions? (Home charging may be absent or lack energy.)
- Does it carry energy (kWh), battery % before/after, and fees — or only a subset? (The
  richer `dx/charging/sessions` pricing/energy endpoint is **business-fleet-only** per the
  docs, so likely unavailable on a personal account.)

### ⚠️ Discovered blocker (2026-07-14): 403 missing scopes

Running the new explorer against `GET /api/1/dx/charging/history` returned **HTTP 403**.
Tesla's FAQ documents 403 as *"Unauthorized missing scopes"* — the token lacks the
endpoint's required scope. This app requests only `openid vehicle_device_data
offline_access` (`internal/auth/oauth.go:13`); charging history needs
**`vehicle_charging_cmds`** (the charging management / billing-history scope). **Source B
is blocked until the token is re-minted with that scope.** Unblock sequence:

1. **Tesla dev portal (Layer 1, user):** ensure the *Magus Monitor* app is permitted to
   request `vehicle_charging_cmds`. If it isn't, the re-consent below is rejected.
2. **Code (`internal/auth/oauth.go`):** add `vehicle_charging_cmds` to the scope string.
   Isolated to `cmd/setup` (per `CLAUDE.md`, `internal/auth` is used only by the setup
   tool — the running web server is unaffected). The multi-tenant web connect flow must
   get the same scope when Source B ships (verify in Tier 2).
3. **Re-consent (user):** re-run `cmd/setup` to redo the OAuth grant (owner grants the new
   scope), writing fresh `.env` tokens; then re-run the explorer to capture the payload.

Fallback: if re-consent WITH the scope still 403s, the endpoint is partner/region-gated
rather than scope-gated — revisit Source B (see Future work).
