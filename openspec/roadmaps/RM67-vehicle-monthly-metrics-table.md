## Intention

`analytics.vehicle_metrics` holds one row per vehicle per **day**. Nothing summarises a **month**.

This roadmap adds `analytics.vehicle_monthly_metrics`: one row per vehicle per month. It stores
the month's distance, efficiency and battery use — split into all days, weekdays and weekends —
plus the month's charging totals and the pack capacity `charging` measured for that month.

The whole table is refreshed by one use case that takes a `tesla_id` and a period (`YYYY-MM`).
Running it again for the same pair rewrites the row. That is the point: it is a sync, not an
append.

## Scope note — why this is a roadmap, not one change

The feature spans **three modules**.

- `charging` owns `monthly_effective_capacity`, and its table comment is explicit:
  *"Owned exclusively by internal/charging; no other module reads this table directly."* So the
  read must become a port. That is tier 1.
- `analytics` owns `vehicle_metrics` and will own the new table and the use case. Tiers 2 and 3.
- `app` owns the nightly cycle, so it owns the trigger. Tier 4.

Tier 1 goes first because tier 2 cannot copy the capacity without it.

## Decisions (binding — settled with the owner on 2026-09-18, before any artifact was written)

Confirmed in a `grill-me` interview, as the ticket asked. Authoritative for every tier. A tier
worker must not re-open them.

### RD1 — Full scope, four tiers, and ONE migration creates the whole table

The owner chose the whole ticket, not a smaller first cut. Tier 2's migration therefore creates
every column, including the `ext_*`, `sc_*` and JSONB columns that tier 3 fills. The table shape
is decided once.

Why: two migrations on one new table is worse than one. A column that tier 3 has not filled yet
reads as `0`, which RD4 already makes a valid value.

### RD2 — Efficiency is `SUM(distance) / SUM(consumed_pct)`, not an average of daily ratios

The monthly efficiency figure is the month's total distance divided by the month's total
`consumed_pct`, over the days where `consumed_pct > 0`. The same rule gives the weekday and the
weekend figures.

Why: a plain `AVG(km_per_pct_calc)` gives a 5 km day the same weight as a 300 km day. Worked
example the owner agreed on — a 300 km day at 50% and a 5 km day at 5%: the average of ratios
says 3.5, the real figure is 305/55 = 5.5.

This is not a new formula. `km_per_pct_calc` is `km / consumed_pct` for one day; this is the same
division over the month's totals. `km_per_pct_calc` itself does not change.

Both rules skip the same days. `km_per_pct_calc` is NULL whenever `consumed_pct <= 0`, and such a
day cannot enter a denominator either. The difference is weighting only.

### RD3 — Refresh every night: the current month AND the previous month

The nightly job syncs two periods per vehicle, every night. Not only the first day of the month.
This **supersedes** the ticket's "first day of the month only".

Why: cost stays flat at `2 x vehicles` per night, whatever the length of history. Re-deriving all
history would grow forever. The owner raised that concern and proposed this window.

Two consequences, both accepted:

- The current month's row describes an **incomplete** month. No column records that. A reader
  compares `period` against today, so a flag would be derived state.
- An edit to a charge older than last month does not heal by itself. It is fixed by running the
  use case for that exact `(tesla_id, period)`. That is why the use case takes a period at all.

`Reconcile` was checked in code first: it is watermark-based over three independent per-source
cursors, so it does not rewrite all history nightly. But editing an old charge moves its
`updated_at` to now, so that old month's `vehicle_metrics` rows DO get rewritten. The drift is
real, and this window bounds it.

### RD4 — Every column is `NOT NULL DEFAULT 0`

No column is nullable. This is the ticket's literal text, and the owner confirmed it after seeing
the alternative.

The cost was stated and accepted: the module's own convention is the opposite
(`internal/analytics/AGENTS.md` — *"absence IS the 'no data' signal ... never a zero"*), so an
efficiency of `0` cannot be told apart from "no data" by the value alone. RD5 is what recovers
that.

### RD5 — A row is always written, plus count columns that make "no data" visible

Every month in the refresh window gets a row, even a month with no input at all. Alongside the
figures the table stores at least one count — how many `vehicle_metrics` days fed the row — so a
reader can tell a real zero from an empty month.

Why: RD4 removed NULL as the "unknown" signal, so the count carries it instead. The sibling table
`charging.monthly_effective_capacity` already does exactly this with `candidate_count` and
`sample_count`. The exact count columns are part of tier 2's design and go through the database
design gate.

### RD6 — The month bucket is `metric_date` itself, never re-projected

March is `metric_date BETWEEN '2026-03-01' AND '2026-03-31'`. No day shifting.

Why: this is not a choice, it is an existing rule. `internal/analytics/AGENTS.md` states *"A
returned `Date` is a FINAL bucket key. It is the row's own already-effective `metric_date` and
must never be re-projected through a caller's own day math."* `metric_date` already carries the
day-before adjustment.

Weekday and weekend come from the ISO day of week of `metric_date`. A `DATE` has no zone, so no
time-zone maths is involved. Weekend is Saturday and Sunday.

### RD7 — The table is `analytics.vehicle_monthly_metrics`

Not `monthly_metrics`.

Why: it sits next to `analytics.vehicle_metrics`, and the pair reads by itself — one per day, one
per month. It is also the name RM52's own RD12 recorded when it deferred this work.

### RD8 — All monthly maths happens in Go, in one place

One query fetches the month's `vehicle_metrics` rows. The Go use case computes every figure from
that slice: all days, weekdays, weekends.

Why: the charging half has no choice — external charges and supercharger sessions arrive through
`charging`'s ports as `[]Entry` and `[]Session`, so they are aggregated in Go anyway. Doing the
`vehicle_metrics` half in SQL would split one month's maths across two places and two testing
styles. A month is about 30 rows, so there is nothing to gain from pushing it down. This is also
what makes the ticket's "isolated and easy to test" true: the maths is unit-testable with no
database.

### RD9 — Only ONE new `charging` port. The other reads already exist

Checked in code, not assumed. See the table above. `Reader.ListEntriesByVehicleBetween` and
`SessionReader.ListSessionsByVehicleBetween` already cover external charges and supercharger
sessions for a date range, and both domain types already carry the energy, cost and
`EndBatteryPct` fields the aggregates need.

Why it matters: the ticket implied several new ports. Adding ports that already exist would widen
`charging`'s public surface for nothing, and each one is a thing the planned microservice split
would have to carry.

### RD10 — The new Go type may not end in a banned generic suffix

`make naming-guard` fails any NEW type whose name ends in `Processor`, `Manager`, `Handler`,
`Helper`, `Data`, `Info`, `Object` or `Thing`. The ticket calls the new thing a "processor", so
the type needs a real name.

The owner also asked that it be built using the installed `golang-*` skills — `golang-naming`,
`golang-code-style`, `golang-design-patterns`, `golang-data-structures`, `golang-documentation`.
They are additive to the project's `ai/go-conventions.md`, never a replacement.
