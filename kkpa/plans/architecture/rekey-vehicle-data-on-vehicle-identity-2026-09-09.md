## Context

Almost every table in this repo is keyed `(account_id, tesla_id, <bucket>)`. That is wrong for
data the platform derives **about a car**: if one vehicle is ever shared (owner + driver), the
same row is stored once per account and the nightly poller recomputes the same history once per
account. `account.vehicles` already answers "which vehicles may this user see" — that is the
only place account identity is needed.

Nothing is broken today: the platform is one-car-per-account, so no row is duplicated yet. This
is a structural correction made **before** vehicle sharing lands.

**Three rules decide every table** — the split is not a judgement call, it follows from whether
the vehicle can be identified on the row:

| Rule | Applies when | Tables |
|---|---|---|
| Key on `tesla_id` | `tesla_id` is `NOT NULL` | `vehicle_snapshots`, `vehicle_metrics`, `vehicle_metric_watermarks`, `charge_gaps` |
| Key on `vin` | `tesla_id` is nullable — the row can exist before the vehicle is known | `telemetry.supercharger_history`, `charging.supercharger_sessions` |
| Keep `account_id`, demoted to an attribute | the row records **who acted**, not what the car did | `manual_charge_entries`, `poll_attempts` |

**Why the `vin` rule exists.** `GET /api/1/dx/charging/history` is an *account-level* Fleet API
call — it takes no vehicle argument, only the account's token. Its sessions carry a **VIN**, and
`telemetry`'s collector resolves `tesla_id` afterwards from a VIN→TeslaID map built from the
account's registered vehicles. A session whose VIN is not currently registered keeps
`tesla_id = NULL`. Those "orphan" rows must stay reachable so they get mirrored once the vehicle
re-registers, and `vin` is `NOT NULL` on both tables. Keying them on `tesla_id` would silently
drop them.

**Tables that do not change:** `account.accounts`, `account.tesla_tokens`, `account.vehicles`
(this is the visibility map), `account.settings`, and `telemetry.poll_runs` (a run-level
aggregate with neither column).

**Checked, not a problem:** `account.settings.analysis_start_date` looked like a per-account
input to car-scoped derivation. It is not — it is only an input-validation floor in the gateway
(`internal/gateway/handlers/external_charges.go`, the `AnalysisStartDateFor` checks) and never
reaches a stored metric.

**The real risk in this whole plan** is not the migrations. Today `WHERE account_id = $1` is the
tenant boundary, enforced in SQL across roughly 40 queries. Even a buggy handler cannot read
another user's data. Section 3 builds the replacement **before** any gateway-facing table loses
the column.

### 3. Build the authorization seam (no table changes)  ·  MAG-66
<!-- Execution order: 3. Prerequisites: section 2 (do it once the pattern is proven, and before any gateway-facing table loses account_id). Goals: G3. -->

This section writes no migration. It replaces the safety net the next three sections remove.

- **Reuse, do not add a port.** `account.Service.RegisteredVehicles(ctx, accountID)` already
  returns the caller's vehicles, and the gateway already calls it in `vehiclesFor`
  (`internal/gateway/handlers/handlers.go`). Do not introduce a second lookup.
- **New shared type.** Create a small package — suggested `internal/vehicleref` — exporting a
  value type (suggested `Ref`) whose `teslaID` field is **unexported**, with a `TeslaID()`
  accessor and a constructor the gateway calls. It must not live in `internal/account`:
  `internal/charging` may not import `account` (that module's design D3), so putting it there
  would make the whole seam unusable in charging.
- **Gateway helper.** Add `authorizeVehicle(ctx, uid, teslaID) (vehicleref.Ref, error)` beside
  the existing `resolveSelectedVehicle` in `internal/gateway/handlers/`. It checks membership in
  `RegisteredVehicles(uid)` and returns 404 — never 403 — when the vehicle is not the caller's,
  so the response does not confirm that the id exists.
- **Why a type and not just a helper.** A helper you can forget to call is not a deterministic
  signal. Once the module ports take `vehicleref.Ref` instead of a bare `int64`, a handler that
  skips the check **fails to compile**. This is a wrapper on a repeated, security-critical
  surface of 30+ methods — the case where indirection pays for itself. Record that rationale in
  the package doc comment.
- **Account-wide reads change shape.** Any port that today filters on `account_id` alone becomes
  "by a list of vehicles": the gateway resolves the list once and passes it down.
- **Docs** — add the rule to `ai/architecture.md` and `internal/gateway/AGENTS.md`: *the gateway
  authorizes the vehicle; modules below it do not check tenancy.*

**Done when:** the package and helper exist, the gateway compiles against them, and a handler
cannot construct a `vehicleref.Ref` without going through the check.

### 4. Re-key the Supercharger pair on `vin`; reshape the mirror  ·  MAG-67
<!-- Execution order: 4. Prerequisites: section 3 (charging.supercharger_sessions is gateway-facing). Goals: G2, G3. -->

The two tables holding the same dataset, both with nullable `tesla_id` and `vin NOT NULL`. Do
them together — splitting them would leave one mirror reading by account and writing by vin.

- **`telemetry.supercharger_history` migration:** keep `UNIQUE (session_id)` as it is. Replace
  `idx_supercharger_history_vehicle_time` with `(vin, charge_start_date_time DESC)`, replace
  `idx_supercharger_history_account_time` and `idx_supercharger_history_account_updated` with
  `(updated_at)` and `(vin, charge_start_date_time DESC)` as the read patterns require. Then
  `DROP COLUMN account_id`.
- **`charging.supercharger_sessions` migration:** replace
  `CONSTRAINT charge_sessions_account_session_unique UNIQUE (account_id, session_id)` with
  `UNIQUE (session_id)`; replace `idx_charge_sessions_vehicle_stop` with
  `(tesla_id, charge_stop_date_time)` — analytics reads this one per registered vehicle, so
  `tesla_id` is right here even though the key is `vin`. Then `DROP COLUMN account_id`.
  Note this table has gained `status` and `inferred_capacity_kwh_calc` since its original
  migration; read the current DDL before writing the change.
- **The mirror loses its per-account shape.** `internal/app/processor.go` currently loops per
  account and calls `SuperchargerHistoryByAccountUpdatedSince`. That query is the **only** one
  that can return a `tesla_id IS NULL` row, and its comment explains why. Replace it with a
  global `SuperchargerHistoryUpdatedSince(since)` and mirror everything in one pass. Preserve
  the orphan-recovery behaviour — verify a row with `tesla_id IS NULL` still reaches
  `charging.SessionWriter.MirrorSessions`.
- **`charging.mirror_watermarks` follows.** It is `UNIQUE (account_id)` because the mirror was
  per-account. With one global pass it becomes a single-row cursor: drop `account_id` and key
  the row on a constant, or replace the table with one row. Keep the "never advance on an empty
  read" rule from its column comment — that rule is why MAG-48 was fixed.
- **`charging.SessionWriter.MirrorSessions`** drops its `accountID` parameter and its
  mis-scoped-account rejection (there is no scope left to mis-state).
- **Gateway** — the Supercharger Stats page reads `charging.SessionReader`. Route its
  per-vehicle reads through section 3's `authorizeVehicle`.
- **Docs** — `internal/telemetry/AGENTS.md`, `internal/charging/AGENTS.md`,
  `openspec/specs/{telemetry,charging}/spec.md`, and both
  `kkpa/context/architecture/telemetry-ingest-only.md` and
  `kkpa/context/workflows/supercharger-stats-read.md`.

**Done when:** both tables have no `account_id`, the mirror runs in one global pass, and an
orphan row (`tesla_id IS NULL`) still round-trips from telemetry into charging.
